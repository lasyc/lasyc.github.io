索引前置准备

Linux 服务器

  1. 云服务
  2. 虚拟机

Linux 安装 Mysql

  1. 使用终端工具连接云服务器，并安装 MySQL
    • apt update
    • apt install mysql-server
  2. MySQL 默认启动，如果未启动，请执行以下命令
    • systemctl start mysql
    • systemctl status mysql
  3. 修改 MySQL 密码。默认情况下，root 用户可能使用的是 auth_socket 插件认证——这种认证方式不要求密码，而是检查当前系统用户是否与 MySQL 用户匹配：如果系统用户是 root，就能免密直接登录
    • mysql -u root -p
    • ALTER USER ‘root‘@’localhost’ IDENTIFIED WITH mysql_native_password BY ‘xxxxxx’;
  4. 创建远程登录用户并授权（xxx.xxx.xxx.xxx 换成你的公网 IP；也可以授权全部库，如 GRANT ALL ON *.* TO ...）
    • CREATE USER ‘root‘@’xxx.xxx.xxx.xxx’ IDENTIFIED WITH mysql_native_password BY ‘xxxxxx’;
    • GRANT ALL ON 库名.* TO ‘root‘@’xxx.xxx.xxx.xxx’;

连接不上原因

  1. 查看 MySQL 服务器的状态，是否启动了
  2. MySQL 密码是否正确
  3. 查看服务器的网络安全组，是否开通了 3306 端口，是否允许本机 IP 访问
  4. 查看 MySQL 服务器的配置文件 /etc/mysql/mysql.conf.d/mysqld.cnf，查看 bind-address 是否是 0.0.0.0

索引概述

索引是一种特殊的数据库结构，用来提高查询效率。除了保存原始数据之外，数据库还会额外维护一份索引：索引指向原始数据，查询时先通过索引定位，就能快速找到目标数据，而不必一行一行扫描整张表

有无索引

  1. 全表扫描：当查询的字段不在索引中时，数据库会全表扫描，即从表中的第一行开始，顺序地读取每一行，直到找到匹配的行
  2. 索引扫描：当查询的字段在索引中时，数据库会通过索引来查找匹配的行索引扫描比全表扫描更快，因为它可以跳过一些行

优缺点

  1. 通过索引可以提高查询效率，且通过索引进行排序可以减少排序的开销
  2. 但是索引需要占用额外的存储空间，且数据库需要维护索引，因此在更新表时，更新索引也会有额外的开销

索引结构

索引是在存储引擎层实现的，因此，根据不同的存储引擎，索引结构也不同

索引结构 描述
B+树索引 最常见的索引，大部分引擎都支持 B+树 索引
Hash索引 底层使用 Hash 表实现，只有精确匹配索引列时才有效，不支持范围查询
R-树索引 空间索引，是 MyISAM 引擎的一个特殊索引类型，用于地理空间数据类型
Full Text索引 全文索引是一种通过倒排索引，快速匹配文档的方式类似于 Lucene、Solr、ES 等全文检索引擎
索引结构 InnoDB MyISAM Memory

Hash索引 √
R-树索引 √
Full Text索引 √ √

B+树索引

B 树：一种多路平衡查找树。与二叉树不同，它的每个节点可以保存多个 key、分出多个分支，因此在相同数据量下树更矮。添加元素时按规则插入到合适位置；当某个节点中的 key 存满（超过上限）时会发生分裂：把中间的 key 提升到父节点，两边的 key 分成左右两个子节点

B+树：B+树是在 B 树基础上做的优化。在 B+树中，除叶子节点以外的其他节点都不保存数据，只作为索引节点保存 key；所有数据都保存在叶子节点中，并且叶子节点之间通过链表首尾相连，方便范围查询时从头到尾顺序扫描

MySQL 中 InnoDB 的 B+树：每个叶子节点（数据页）会额外保存指向相邻叶子页的指针，查询时顺着链表就能连续读出一个范围内的数据

Hash 索引

Hash 索引是一种基于哈希函数的数据结构，先将索引字段的值作为键值，计算出每个键值的哈希值，存入哈希表中，并且在哈希表中保存原始数据的位置

特点：

  1. 只支持等值比较，如：=、in，不支持范围查询，如：>、<、between等
  2. 无法利用索引进行排序
  3. 等值查询的效率通常高于 B+树索引（直接对哈希值定位，无需从根节点一层层向下查找）

在 MySQL 中，只有 Memory 存储引擎原生支持 Hash 索引。不过 InnoDB 还具备自适应哈希索引（Adaptive Hash Index）能力：当某个 B+树索引被频繁等值访问时，InnoDB 会在内存中自动为其构建哈希索引来加速，整个过程无需手动干预

为什么 InnoDB 存储引擎使用 B+树索引

  1. B+树 相比于二叉树、红黑树等结构，在相同数据量的情况下层级更少、查询要访问的节点更少，效率更高（数据量越大优势越明显）
  2. B+树 的非叶子节点只保存索引 key、不保存原始数据，因此同样一个页（默认 16KB）能装下更多的 key；而 B 树的非叶子节点也要保存数据，同样空间装下的 key 就少。所以在同等存储空间下，B+树 能索引更多的数据、树更矮

索引的分类

分类

类型 描述 个数 关键字
主键索引 针对于表中主键所创建的索引 主键会自动创建索引，只能有一个 PRIMARY
唯一索引 索引中不允许有重复的值 可以有多个 UNIQUE
普通索引 快速定位指定数据 可以有多个
全文索引 全文索引匹配的是文本中的关键字 可以有多个 FULLTEXT

聚集索引和非聚集索引

在 InnoDB 中，根据索引的存储形式，又可以分为两类：

索引存储形式 索引类型 特点
聚集索引 索引和数据一起存储，索引中存储的是数据本身 有且只能一个
二级索引(非聚集索引) 索引和数据分开存储，索引中存储的是数据的主键值 可以有多个

聚集索引有且只有一个，所以不需要我们自己创建，默认的规则为：

  1. 如果存在主键，主键索引就是聚集索引
  2. 如果不存在主键，则使用第一个唯一索引作为聚集索引
  3. 如果以上均不存在，InnoDB 会自动生成一个隐藏的 rowid 列（6 字节）作为聚集索引

回表

  • 通过二级索引查到数据的主键值后，还要拿着主键值再到聚集索引里查一次原始数据，这个”二次查找”的过程就叫回表（查询中回表次数越少，性能越好）

练习

以下两个 SQL 语句，执行效率哪个更高？

InnoDB 主键索引的 B+树 高度大约是多少？

主键索引就是聚集索引：非叶子节点不保存整行数据，只保存主键值（key）和指针，且指针个数 = key 个数 + 1。

假设主键类型为 int（4 字节）、指针占 6 字节，一个节点存放在一个页中（一页 16KB = 16 × 1024 字节）。设一个页最多能放 m 个 key，则：

m × 4 + (m + 1) × 6 = 16 × 1024，解得 m ≈ 1637

也就是说一个非叶子节点大约能存 1637 个主键值和 1638 个指针。如果一行数据约 1KB，一个叶子页能放 16 行数据，那么：

  • 两层高的 B+树 能存约 1637 × 16 ≈ 2.6 万条数据
  • 三层高的 B+树 能存约 1637 × 1637 × 16 ≈ 4287 万条数据

所以千万级数据的表，B+树 通常只有 3~4 层，查询时最多访问几次磁盘就能定位到数据。

索引语法

创建索引

CREATE [UNIQUE | FULLTEXT] INDEX index_name ON table_name (column_name1, column_name2, …);

查看索引

SHOW INDEX FROM table_name;

删除索引

DROP INDEX index_name ON table_name;
