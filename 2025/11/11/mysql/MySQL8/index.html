索引前置准备

Linux 服务器

  1. 云服务
  2. 虚拟机

Linux 安装 Mysql

  1. 使用终端工具连接云服务器，并安装 MySQL
    • apt update
    • apt install mysql-server
  2. MySQL 默认启动，如果未启动，请执行以下命令
    • systemctl start mysql
    • systemctl status mysql
  3. 修改 MySQL 密码。默认情况下，root 用户可能使用的是 auth_socket 插件认证——这种认证方式不要求密码，而是检查当前系统用户是否与 MySQL 用户匹配：如果系统用户是 root，就能免密直接登录
    • mysql -u root -p
    • ALTER USER ‘root‘@’localhost’ IDENTIFIED WITH mysql_native_password BY ‘xxxxxx’;
  4. 创建远程登录用户并授权（xxx.xxx.xxx.xxx 换成你的公网 IP；也可以授权全部库，如 GRANT ALL ON *.* TO ...）
    • CREATE USER ‘root‘@’xxx.xxx.xxx.xxx’ IDENTIFIED WITH mysql_native_password BY ‘xxxxxx’;
    • GRANT ALL ON 库名.* TO ‘root‘@’xxx.xxx.xxx.xxx’;

连接不上原因

  1. 查看 MySQL 服务器的状态，是否启动了
  2. MySQL 密码是否正确
  3. 查看服务器的网络安全组，是否开通了 3306 端口，是否允许本机 IP 访问
  4. 查看 MySQL 服务器的配置文件 /etc/mysql/mysql.conf.d/mysqld.cnf，查看 bind-address 是否是 0.0.0.0

索引概述

索引是一种特殊的数据库结构，用来提高查询效率。除了保存原始数据之外，数据库还会额外维护一份索引：索引指向原始数据，查询时先通过索引定位，就能快速找到目标数据，而不必一行一行扫描整张表

有无索引

  1. 全表扫描：当查询的字段不在索引中时，数据库会全表扫描，即从表中的第一行开始，顺序地读取每一行，直到找到匹配的行
  2. 索引扫描：当查询的字段在索引中时，数据库会通过索引来查找匹配的行索引扫描比全表扫描更快，因为它可以跳过一些行

优缺点

  1. 通过索引可以提高查询效率，且通过索引进行排序可以减少排序的开销
  2. 但是索引需要占用额外的存储空间，且数据库需要维护索引，因此在更新表时，更新索引也会有额外的开销

索引结构

索引是在存储引擎层实现的，因此，根据不同的存储引擎，索引结构也不同

索引结构 描述
B+树索引 最常见的索引，大部分引擎都支持 B+树 索引
Hash索引 底层使用 Hash 表实现，只有精确匹配索引列时才有效，不支持范围查询
R-树索引 空间索引，是 MyISAM 引擎的一个特殊索引类型，用于地理空间数据类型
Full Text索引 全文索引是一种通过倒排索引，快速匹配文档的方式类似于 Lucene、Solr、ES 等全文检索引擎
索引结构 InnoDB MyISAM Memory

Hash索引 √
R-树索引 √
Full Text索引 √ √

B+树索引

B 树：一种多路平衡查找树。与二叉树不同，它的每个节点可以保存多个 key、分出多个分支，因此在相同数据量下树更矮。添加元素时按规则插入到合适位置；当某个节点中的 key 存满（超过上限）时会发生分裂：把中间的 key 提升到父节点，两边的 key 分成左右两个子节点

B+树：B+树是在 B 树基础上做的优化。在 B+树中，除叶子节点以外的其他节点都不保存数据，只作为索引节点保存 key；所有数据都保存在叶子节点中，并且叶子节点之间通过链表首尾相连，方便范围查询时从头到尾顺序扫描

MySQL 中 InnoDB 的 B+树：每个叶子节点（数据页）会额外保存指向相邻叶子页的指针，查询时顺着链表就能连续读出一个范围内的数据

Hash 索引

Hash 索引是一种基于哈希函数的数据结构，先将索引字段的值作为键值，计算出每个键值的哈希值，存入哈希表中，并且在哈希表中保存原始数据的位置

特点：

  1. 只支持等值比较，如：=、in，不支持范围查询，如：>、<、between等
  2. 无法利用索引进行排序
  3. 等值查询的效率通常高于 B+树索引（直接对哈希值定位，无需从根节点一层层向下查找）

在 MySQL 中，只有 Memory 存储引擎原生支持 Hash 索引。不过 InnoDB 还具备**自适应哈希索引（Adaptive Hash Index）**能力：当某个 B+树索引被频繁等值访问时，InnoDB 会在内存中自动为其构建哈希索引来加速，整个过程无需手动干预

为什么 InnoDB 存储引擎使用 B+树索引

  1. B+树 相比于二叉树、红黑树等结构，在相同数据量的情况下层级更少、查询要访问的节点更少，效率更高（数据量越大优势越明显）
  2. B+树 的非叶子节点只保存索引 key、不保存原始数据，因此同样一个页（默认 16KB）能装下更多的 key；而 B 树的非叶子节点也要保存数据，同样空间装下的 key 就少。所以在同等存储空间下，B+树 能索引更多的数据、树更矮

索引的分类

分类

类型 描述 个数 关键字
主键索引 针对于表中主键所创建的索引 主键会自动创建索引，只能有一个 PRIMARY
唯一索引 索引中不允许有重复的值 可以有多个 UNIQUE
普通索引 快速定位指定数据 可以有多个
全文索引 全文索引匹配的是文本中的关键字 可以有多个 FULLTEXT

聚集索引和非聚集索引

在 InnoDB 中，根据索引的存储形式，又可以分为两类：

索引存储形式 索引类型 特点
聚集索引 索引和数据一起存储，索引中存储的是数据本身 有且只能一个
二级索引(非聚集索引) 索引和数据分开存储，索引中存储的是数据的主键值 可以有多个

聚集索引有且只有一个，所以不需要我们自己创建，默认的规则为：

  1. 如果存在主键，主键索引就是聚集索引
  2. 如果不存在主键，则使用第一个唯一索引作为聚集索引
  3. 如果以上均不存在，InnoDB 会自动生成一个隐藏的 rowid 列（6 字节）作为聚集索引

回表

  • 通过二级索引查到数据的主键值后，还要拿着主键值再到聚集索引里查一次原始数据，这个”二次查找”的过程就叫回表（查询中回表次数越少，性能越好）

练习

以下两个 SQL 语句，执行效率哪个更高？

InnoDB 主键索引的 B+树 高度大约是多少？

主键索引就是聚集索引：非叶子节点不保存整行数据，只保存主键值（key）和指针，且指针个数 = key 个数 + 1。

假设主键类型为 int（4 字节）、指针占 6 字节，一个节点存放在一个页中（一页 16KB = 16 × 1024 字节）。设一个页最多能放 m 个 key，则：

m × 4 + (m + 1) × 6 = 16 × 1024，解得 m ≈ 1637

也就是说一个非叶子节点大约能存 1637 个主键值和 1638 个指针。如果一行数据约 1KB，一个叶子页能放 16 行数据，那么：

  • 两层高的 B+树 能存约 1637 × 16 ≈ 2.6 万条数据
  • 三层高的 B+树 能存约 1637 × 1637 × 16 ≈ 4287 万条数据

所以千万级数据的表，B+树 通常只有 3~4 层，查询时最多访问几次磁盘就能定位到数据。

索引语法

创建索引

CREATE [UNIQUE | FULLTEXT] INDEX index_name ON table_name (column_name1, column_name2, …);

查看索引

SHOW INDEX FROM table_name;

删除索引

DROP INDEX index_name ON table_name;

SQL 性能分析

SQL 性能分析：通过分析 SQL 语句，了解它在数据库中的实际执行情况（是否走了索引、扫描了多少行、耗时多少等），再根据分析结果有针对性地优化 SQL

SQL 执行频率

SHOW [SESSION|GLOBAL] STATUS LIKE ‘Com**__**’;

慢查询日志

在慢查询日志中，记录了所有执行时间超过了执行阈值的 SQL 查询语句

  1. 查看慢查询日志开关状态

    SHOW VARIABLES LIKE ‘slow_query_log’;

  2. 开启慢查询日志(临时)

    SET [SESSION|GLOBAL] slow_query_log = ON;

  3. 开启慢查询日志(持久)

    修改配置文件 /etc/my.cnf 或者 /etc/mysql/my.cnf，添加参数：slow_query_log=1 和 long_query_time=2，然后重启 MySQL 服务器

profile 详情

慢查询日志只能记录”超过阈值”的 SQL。如果某条 SQL 本身很简单、执行时间没达到阈值，却明显比平时慢（比如从 1ms 涨到 30ms），慢查询日志就发现不了它。这时可以用 profile 查看每条 SQL 执行时各个阶段的耗时，精确定位慢在哪一步

  1. 查看当前数据库是否支持 profile

    SELECT @@have_profiling;

  2. 查看 profile 是否开启

    SELECT @@profiling;

  3. 开启 profile

    SET profiling = 1;

  4. 查看 profile 详情

    SHOW PROFILES;

  5. 查看指定 profile 详情

    SHOW PROFILE FOR QUERY [QUERY_ID];

性能分析 explain

explain 命令可以查看 SQL 语句的执行计划，根据执行计划可以判断 SQL 语句的性能

EXPLAIN 查询语句;

查询结果

  • id：SELECT 或操作表的顺序。id 越大越先执行；id 相同时从上到下依次执行
  • select_type：SQL 语句的类型，常见的有：SIMPLE（简单查询）、PRIMARY（主查询）、SUBQUERY（子查询）等
  • type：访问类型，常见的有：NULL（不访问任何表，如 SELECT 1）、system（系统表）、const（按主键/唯一索引等值查，最多一行）、eq_ref（联表时按主键/唯一索引各查一行）、ref（按普通索引等值查）、range（范围查询）、index（扫描整棵索引树）、ALL（全表扫描）。从左到右性能依次变差
  • possible_keys：可能用到的索引（优化器评估后不一定真的使用）
  • key：实际使用的索引（NULL 表示没走索引）
  • key_len：本次查询实际用到的索引长度（字节），可以用来判断联合索引用到了哪几列
  • rows：预计扫描的行数（估算值，不是实际返回的行数）
  • filtered：过滤后预计剩余的行数占 rows 的百分比。例如 rows=24、filtered=10.00，表示扫描 24 行后大约只剩 2 行左右符合条件；越接近 100% 说明过滤效果越好

性能分析总结

  1. 查看 SQL 语句的执行频次：SHOW [SESSION|GLOBAL] STATUS LIKE 'Com______';
  2. 查看慢查询日志：SHOW VARIABLES LIKE '%slow_query_log%';、cat /var/log/mysql/mysql-slow.log
  3. 查看 Profile 详情：SHOW PROFILES;、SHOW PROFILE FOR QUERY [QUERY_ID];
  4. 查看 SQL 语句的执行计划：EXPLAIN 查询语句;

使用索引

示例

最左前缀法则

如果一个索引是由多个列组成的复合索引，那么在查询中，若想使用该索引，则必须满足最左前缀法则：查询条件必须从索引最左侧的列开始、且中间不能断开。

举例：若存在联合索引（A, B, C, D），那么：

  1. 条件包含 (A, B, C, D) → 四列全部生效
  2. 条件包含 (A, B, C) → A、B、C 三列生效
  3. 条件包含 (A, B) → A、B 两列生效
  4. 条件只包含 (A) → 只有 A 生效
  5. 条件包含 (B, C, D)：缺少最左侧的 A，不满足最左前缀，索引完全失效
  6. 条件包含 (A, C, D)：虽然 A 在最左侧，但跳过了中间的 B（不连续），因此只有 A 生效，C、D 都用不上

范围查询

在联合索引中，一旦某列使用了范围查询（>、<），该列右侧的列就无法使用索引（范围条件就像一个”断点”）。而 >=、<= 因为能转化为等值边界，通常不会断开索引

索引列运算

不要在索引列上进行运算，否则会导致索引失效

类型转换

字符串类型字段不加单引号，索引失效

前缀模糊查询

模糊查询时，若通配符 % 出现在字符串开头，则索引失效

OR 查询

使用 OR 连接多个条件时，若其中一个条件未使用索引，则整个查询无法使用索引

数据分布影响

当使用索引时，MySQL 会根据数据的分布情况来决定是否使用索引如果某个条件过滤掉的数据量很小，MySQL 可能会选择全表扫描而不是使用索引，因为全表扫描可能更高效

SQL 提示

在 MySQL 中，可以使用 SQL 提示来强制使用索引或避免使用索引

语法 描述
USE INDEX (index_list) 提示优化器在查询时使用指定的（建议）
IGNORE INDEX (index_list) 提示优化器在查询时忽略指定的索引（建议）
FORCE INDEX (index_list) 强制优化器在查询时使用指定的索引（强制）

覆盖索引

覆盖索引指索引包含查询所使用的列，避免回表

  1. Using index condition：表示使用了索引条件下推（Index Condition Pushdown，ICP），即在索引扫描阶段就过滤掉不符合条件的行，减少回表的行数，从而提高查询效率
  2. Using where; Using index：表示查询使用了索引，并且索引包含了查询所需的所有列，因此不需要回表，直接从索引中获取数据

前缀索引

当数据库中某个字段保存的内容过长，比如一篇文章，在这种情况下，若对该字段建立索引，开销会很大，因此可以使用前缀索引，只对字段的前几个字符建立索引，从而减少索引的大小，提高查询效率

CREATE INDEX idx_xxx ON tb_xxx(column(n));

前缀长度怎么定？

根据索引选择性来定：选择性 = 该字段去重后的取值个数 ÷ 总行数（最大为 1）。选择性越接近 1，说明区分度越高、索引效果越好。实际做法是：分别测试不同前缀长度的选择性，在区分度没有明显下降的前提下，前缀取得越短越好（越省空间）

索引选择

索引的选择，应该遵循以下原则：

  1. 索引数量要克制：只为高频查询、排序、分组涉及的列建索引（每多一个索引，插入/更新时都要额外维护，写性能会下降）
  2. 优先选区分度高（选择性接近 1）的列，过滤效果更好
  3. 字段值很长时，用前缀索引来缩小索引体积
  4. 多个列经常一起作为查询条件时，建联合索引而不是多个单列索引（查询列都能从索引取到时还能避免回表）

索引设计

  1. 当表的数据量较大时，且查询频繁时，应该考虑创建索引
  2. 对于经常作为查询、排序、分组条件的列，应该考虑创建索引
  3. 尽量使用区分度高的列作为索引列
  4. 若字段中的值过长，可以考虑使用前缀索引
  5. 多个列经常组合查询时，尽量用联合索引而不是多个单列索引；查询列都能从索引中取到时还能避免回表
  6. 索引不是越多越好，应该平衡索引和查询性能

索引总结

  1. 索引概述：索引是一种数据结构，用于加速数据查询
  2. 索引结构：B+树索引、哈希索引等
  3. 索引分类：
    • 唯一索引、普通索引、组合索引、全文索引
    • 聚集索引、非聚集索引
  4. 索引语法：
    • 创建索引：CREATE INDEX index_name ON table_name (column_name);
    • 删除索引：DROP INDEX index_name ON table_name;
    • 查看索引：SHOW INDEX FROM table_name;
  5. SQL 性能分析：
    • 执行频次、慢查询日志、profile、explain
  6. 索引使用：
    • 最左前缀法则，不满则不使用索引
    • 范围查询，使用等值查询，而不是范围查询，范围查询后续列索引失效
    • 索引列运算，不使用索引
    • 类型转换，不使用索引
    • 前缀模糊查询，不使用索引
    • OR 查询，若 OR 语句两侧的查询条件中有一个没有索引，则 OR 语句将无法使用索引
    • 数据分布影响，若数据量过小，或者查询条件筛选过少，则放弃索引，扫描全表
    • SQL 提示，当某个字段拥有多个索引时，可以指定使用哪一个索引
    • 覆盖索引，尽量让索引包含查询返回字段，避免回表
    • 前缀索引，当字段值过长时，可以创建前缀索引，取前 N 个字符作为索引

MySQL 日志
错误日志错误日志是 MySQL 中最重要的一类日志，记录了 MySQL 在启动、运行、停止过程中出现的严重错误信息。当数据库出现异常无法正常使用时，应该第一时间查看这个日志。 错误日志默认开启，默认存放在 /var/log 目录下，文件名为 mysqld.log；也可以通过 log_error 系统变量查看（或指定）日志文件的位置 二进制日志二进制日志（binlog）中记录了所有会导致数据变化的操作：DDL 和 DML 语句（不记录 DQL 查询）。MySQL 8.0 起二进制日志默认开启。 注意区分：binlog 是 Server 层的逻辑日志（记录已提交的操作），用于数据恢复和主从复制；redo log 是 InnoDB 引擎层的物理日志（记录数据页的修改），用于崩溃恢复。 二进制日志文件的具体位置可以通过 log_bin 等系统变量查看 123456789101112mysql> SHOW VARIABLES LIKE '%log_bin%';+---------------------------------+----------------...
