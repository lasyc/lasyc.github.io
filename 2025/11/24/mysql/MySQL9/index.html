MySQL SQL 优化

插入优化

普通插入

插入一条数据

批量插入

当需要插入多条数据时，不建议一条一条地执行 INSERT，而是把多条数据放在同一条 INSERT 语句里批量插入。

虽然批量插入效率高，但单条 INSERT 塞太多行也会有其他开销，经验上以 1000 行左右为一组比较合适，数据更多时可以拆成多条分批插入（MySQL 本身没有 1000 条的限制，主要受 max_allowed_packet 等参数影响）。

事务提交

MySQL 默认是自动提交事务的，所以执行多条插入语句时，每一条都会提交一次事务，性能较差。我们可以手动开启事务：先 START TRANSACTION，执行完所有插入语句后再统一 COMMIT。这样多次插入只需要一次事务提交，性能会提高很多

主键顺序

插入数据时，尽量按照主键的顺序插入（例如自增主键天然有序）。如果主键乱序插入，很容易引发数据页分裂（见下文），影响插入性能

大批量插入

虽然批量插入能一次插多行，但性能仍然有限。当数据量达到几十万甚至上百万行时，推荐使用 MySQL 提供的 LOAD DATA 指令进行批量导入，速度会快很多。

操作步骤：

  1. 连接数据库时添加参数：mysql --local-infile -u root -p
  2. 修改全局配置：SET GLOBAL local_infile = 1;
  3. 准备好数据文件后，使用 LOAD DATA 命令批量导入：LOAD DATA LOCAL INFILE '/root/data.csv' INTO TABLE tb_user FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n';

注意：如果数据文件里没有主键 id 这一列，需要在表名后指定列名，例如 INTO TABLE tb_user (name, phone, email, ...)，否则数据会错位。

主键优化

数据组织方式

在 InnoDB 存储引擎中，数据是按照主键的顺序存储的，这种存储方式的表称为索引组织表（IOT）。因此设计表结构时，尽量选择有序增长的主键（如自增主键），这样插入数据时能按顺序追加到数据页末尾，减少页分裂，提高插入性能

页分裂

前面学过，InnoDB 中数据是以页为单位存储的，默认页大小为 16KB。InnoDB 规定单行记录的总大小不能超过页大小的一半，因此每页至少能存两条记录，即一条记录一般不超过 8KB。如果单行数据实在太大放不下，就会发生行溢出，超出的部分会被存到单独的溢出页中。

当主键顺序插入时，数据会顺序追加到当前页的末尾；当前页填满后，就新建一个页继续追加：

而当主键乱序插入时，数据要插到页中间的正确位置。如果目标页已经填满，装不下新数据，就需要把部分数据挪到新页——这个过程叫页分裂，会造成额外的性能损耗：

页合并

当删除数据时，若某个页中的数据被删除后，剩余数据量小于指定的阈值时，则会发生页合并，将该页的数据与相邻的页合并，从而释放该页

该阈值可以通过 MERGE_THRESHOLD 参数进行设置，默认值为 50%

主键设计原则

  1. 尽量降低主键的长度
  2. 尽量选择自增主键，或者其他递增主键，尽量按照顺序插入数据
  3. 尽量不要使用 UUID 等随机主键：UUID 没有规律，插入时很容易触发页分裂，影响插入性能；而且 UUID 比较长，会增大索引体积，影响查询性能

排序优化

在 MySQL 中，排序操作分为两种：

  1. Using filesort：文件排序。先把数据读到内存的排序缓冲区（sort buffer）中排序，内存不够时会把中间结果写到磁盘临时文件再归并排序，性能较差
  2. Using index：索引排序。直接利用索引本身的有序性，按索引顺序读取数据即可，不需要额外排序，性能较好

分组优化

分页优化

使用 LIMIT 进行分页查询时，页数（偏移量）越大，性能越差：MySQL 需要先扫描并丢弃前面的所有行，再返回目标页的数据（比如 LIMIT 1000000, 10 也要先扫过前 100 万行）。

优化思路：

  1. 使用覆盖索引，先只查出目标行的主键，再根据主键回表查完整数据
  2. 通过子查询的方式：子查询里只查主键并分页，外层再用主键关联取整行数据

提醒：分页查询一般要配合 ORDER BY，否则”每一页取哪些行”是不确定的。

COUNT 优化

在 MyISAM 中，COUNT(*)（不带 WHERE 条件时）不需要实时计算：MyISAM 会专门维护一个行数计数器，直接返回计数器的值即可，所以非常快。

在 InnoDB 中，没有单独维护行数，COUNT(*) 需要把数据一行行读出来统计，所以比 MyISAM 慢（事务隔离要求不同事务看到不同的行数，无法提前缓存）。

目前 MySQL 暂时没有特别完美的内置方案，实际项目中常用一些替代手段：例如在 Redis 中维护一个计数器，插入数据时 +1、删除数据时 -1，用近似值来扛住高并发的计数需求（注意它只是一个近似值，需要容忍短暂的不一致）。

COUNT 分类

分类 描述
COUNT(*) 统计行数，不取值，直接累加行数，性能最高
COUNT(主键) 统计行数，取值，性能一般
COUNT(column) 统计该列非 NULL的行数（NULL 不计数），需要判断取值，性能一般
COUNT(1) 统计行数，不取值，直接累加行数，性能约等于 COUNT(*)

更新优化

在事务中执行 UPDATE（或 DELETE）时，会对涉及的行上锁，直到事务结束（提交或回滚）才会释放，期间其他会话无法操作这些数据。

  1. 如果 WHERE 条件能用到索引，InnoDB 加的是行级锁（准确说是对索引记录加锁），只锁住符合条件的行，其他行不受影响
  2. 如果 WHERE 条件无法走索引，InnoDB 只能对整张表逐行扫描加锁（同时还会锁间隙），相当于锁住了整张表，其他会话的操作都会被阻塞

补充：InnoDB 本身没有传统意义上的表级锁（锁定整张表）用于普通 DML，但”扫描全表并逐行加锁”的效果和锁表差不多，所以说法上常被简称为锁表。

因此，执行 UPDATE / DELETE 时，WHERE 条件里一定要包含能走索引的列，避免全表加锁、影响并发。

总结

  1. 插入优化：批量插入，手动提交事务，主键按顺序插入，大批量数据使用 LOAD DATA 命令
  2. 主键优化：主键长度要短，尽可能按顺序插入，避免页分裂
  3. 排序优化：创建合适的索引，满足最左前缀法则，尽可能使用 Using index，避免 Using filesort
  4. 分组优化：创建合适的索引，满足最左前缀法则
  5. 分页优化：使用索引覆盖，子查询主键，再通过主键查询数据
  6. COUNT 优化：使用 COUNT(*) 或 COUNT(主键)，避免 COUNT(column)
  7. 更新优化：UPDATE / DELETE 的 WHERE 条件要能走索引，避免全表加锁
