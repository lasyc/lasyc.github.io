MySQL InnoDB 引擎

发表于2025-12-09|更新于2026-09-03
|浏览量:

逻辑存储结构

  1. 表空间（Tablespace）：一个 MySQL 实例可以对应多个表空间，用于存储记录、索引等数据，一个表空间内含有多个段（Segment）
  2. 段（Segment）：分为数据段（Leaf node segment）、索引段（Non-leaf node segment）、回滚段（Rollback segment）。InnoDB 是索引组织表：数据段就是 B+ 树的叶子节点（真正存数据），索引段就是 B+ 树的非叶子节点（存索引），一个段内含有多个区（Extent）
  3. 区（Extent）：每个区的大小为 1M。默认情况下，一个区含有 64 个页（Page），也就是每页 16K
  4. 页（Page）：InnoDB 最小的存储单元，每页 16K。为了尽量保证页在磁盘上的连续性，InnoDB 按区申请空间，每次会申请 4 ~ 5 个区
  5. 行（Row）：表中的每一行记录。除用户定义的数据列外，每行还带有隐藏字段：Trx_id（最后一次修改该行的事务 id）和 Roll_pointer（回滚指针，指向该行上一个版本的 undo log 记录）

架构

从 MySQL 5.5 开始，InnoDB 成为默认存储引擎。在架构上，InnoDB 分为内存架构（Buffer Pool、Log Buffer 等）和磁盘架构（系统表空间、redo log 文件等）两部分

内存架构

Buffer Pool

缓冲池（Buffer Pool）是主内存中的一块区域，用于缓存经常访问的数据页。操作数据时，会先判断数据页是否已在缓冲池中：存在就直接读写缓冲池中的数据（被修改的页之后由后台线程统一刷入磁盘），可以大幅减少磁盘 IO；不存在则先从磁盘把数据页加载进缓冲池，再继续操作。

缓冲池的最小管理单位是页（Page），底层用链表来管理这些页。每个页有三种状态：

  1. Free：空闲页，还没有存放数据
  2. Clean：已被使用，但数据没有被修改过（与磁盘内容一致）
  3. Dirty：已被使用，且数据被修改过（与磁盘内容不一致，即脏页，需要刷盘）

Change Buffer

更改缓冲区，只用于非唯一二级索引页，在执行 DML 语句时，如果缓冲池中不存在数据，会将数据变更保存在这里，等待未来数据被读取时，再将原始数据与被修改后的数据合并，并存入缓冲池，之后再由缓冲池将数据写入磁盘

Adaptive Hash Index

自适应哈希索引，用于优化对缓冲池中数据的查询，InnoDB 引擎会自动检测每个索引页，如果观测到 Hash 索引可以提升查询速度，则建立 Hash 索引，因此称为自适应哈希索引

自适应哈希索引的开启可以通过 innodb_adaptive_hash_index 全局参数来控制，默认为 ON

Log Buffer

日志缓冲区，用来保存要写入磁盘的日志信息（redo log、undo log），默认大小为 16MB，日志缓冲区的日志会定期写入到磁盘中，适当增加缓冲区的大小，可以减少磁盘IO

日志缓冲区的大小可以通过 innodb_log_buffer_size 全局参数控制，默认大小为 16777216
日志缓冲区的日志写入时机可以通过 innodb_flush_log_at_trx_commit 全局参数控制，默认值为 1

  • 0：不主动刷盘，由后台线程每秒刷一次。性能最好，但 MySQL 崩溃时可能丢失最近 1 秒内已提交的事务
  • 1：每次事务提交时都把日志刷入磁盘（默认值）。最安全，但每次提交都多一次磁盘 IO
  • 2：每次提交只把日志写入操作系统缓存，由后台线程每秒刷盘一次。性能折中，操作系统（机器）崩溃时可能丢最近 1 秒数据

磁盘架构

System Tablespace

系统表空间（System Tablespace）主要存放 InnoDB 的数据字典、更改缓冲区（Change Buffer）等系统级数据，位置和大小由 innodb_data_file_path 参数指定

File-Per-Table-Tablespaces

每表文件表空间（File-Per-Table）：每个表的数据和索引各自保存在独立的 .ibd 文件中，由 innodb_file_per_table 参数控制，默认开启，因此每张表都会有对应的数据文件

General Tablespaces

通用表空间（General Tablespace）：需要通过 CREATE TABLESPACE 语法手动创建，建表时可以用 CREATE TABLE ... TABLESPACE xxx 把表放进指定的表空间

  1. 创建表空间

    CREATE TABLESPACE 表空间名 ADD DATAFILE ‘文件名’ ENGINE=引擎名;

  2. 指定表空间

    CREATE TABLE 表名 … TABLESPACE 表空间名;

Undo Tablespaces

撤销表空间，用于存储 undo log 日志，每个 MySQL 实例在初始化时都会创建两个默认的撤销表空间，默认大小为 16MB

Temp Tablespaces

临时表空间，用于存储创建的临时表

Doublewrite Buffer Files

双写缓冲区，为了保证数据安全，InnoDB 引擎在将数据页的数据从缓冲池中写入到磁盘前，会先将数据读入到双写缓冲区，以便系统异常时恢复数据

文件名：#ib_16384_0.dblwr 和 #ib_16384_1.dblwr

Redo Log

重做日志（redo log），用来实现事务的持久性。它由两部分组成：内存中的重做日志缓冲区（redo log buffer）和磁盘上的重做日志文件（redo log file）。采用 WAL（Write-Ahead Logging，日志先行）机制：事务执行过程中对数据页的修改会先记录到 redo log，事务提交时保证日志已落盘。之后即使脏页还没刷回磁盘就发生宕机，重启时也能根据 redo log 把修改重放出来，保证不丢数据

文件名：ib_logfile0 和 ib_logfile1

后台线程

后台线程用于将缓冲池中的数据在合适的时机写入到磁盘文件中

Master Thread

核心后台线程，负责调度其他线程，还负责将缓冲池的数据异步写入到磁盘文件中，保持数据的一致性，还包括脏页的刷新、合并插入缓存、undo 页的回收

IO Thread

InnoDB 引擎中大量的使用了 AIO 来处理 IO 请求，这样可以极大的提高数据库的性能，IO Thread 主要负责这些 IO 请求的回调

线程类型 默认个数 作用
Read Thread 4 负责读操作
Write Thread 4 负责写操作
Log Thread 1 负责将日志缓冲区的数据写入到磁盘
Insert buffer Thread 1 负责将写缓冲区的数据写入到磁盘

Purge Thread

用于回收当事务提交之后的 undo log，当事务提交后，undo log 就没用了，使用此线程回收

Page Cleaner Thread

协助 Master Thread 将脏页数据写入到磁盘中，减轻 Master Thread 的压力，减少阻塞

事务原理

事务是一组操作的集合，是不可分割的工作单位：事务中的所有操作要么全部成功，要么全部失败。

事务的特性（ACID）：

  1. 原子性（Atomicity）：事务是不可分割的最小操作单元
  2. 一致性（Consistency）：事务完成时，数据从一个一致状态变为另一个一致状态
  3. 隔离性（Isolation）：一个事务的执行不会被其他并发事务干扰
  4. 持久性（Durability）：事务一旦提交，对数据的修改就是永久性的

其中：原子性、一致性由 undo log（回滚）与 redo log（崩溃恢复）配合保证，持久性由 redo log 保证；隔离性则由锁和 MVCC 实现

Redo log

重做日志，用于记录事务提交时对数据页所做的物理修改，以此来实现持久性

该日志由两部分组成：内存中的重做日志缓冲区（redo log buffer）和磁盘上的重做日志文件（redo log file）。事务提交时会把所有修改记录写入重做日志文件；之后缓冲池把脏页刷回磁盘时如果发生宕机，可以根据日志把修改重放，保证不丢数据

Undo log

回滚日志，用于记录数据被修改前的信息，当发生回滚时，可以根据 Undo log 中的记录逆向恢复数据

当我们在操作数据时，会在 undo log 中记录与操作相反的内容：比如执行了 DELETE，undo log 会记录一条对应的 INSERT；执行了 UPDATE，undo log 会记录修改前的旧值。这样当执行 ROLLBACK 时，就可以通过 undo log 中的记录逆向恢复数据，实现数据回滚，保证事务的原子性

事务创建时也会创建 undo log，但是当事务结束时（提交或者回滚），并不会立即销毁 undo log，这些日志可能还用于 MVCC

undo log 存放在回滚段（rollback segment）中，其中包含 1024 个 undo log segment

MVCC

当前读

当前读：读取的是记录的最新版本，且读取时要确保其他事务不能修改当前记录，所以会对记录进行加锁如：SELECT ... LOCK IN SHARE MODE 、SELECT ... FOR UPDATE、INSERT、UPDATE、DELETE 等

快照读

快照读，即简单的 SELECT 语句，读取的是记录的可见版本，有可能不是最新版而是历史数据，因此不需要加锁，是非阻塞读

隔离级别 快照读
Read Committed 每次执行 SELECT 语句，都会生成一个新的快照读
Repeatable Read 第一个 SELECT 语句会生成快照读，后续的重复的 SELECT 直接读取快照读数据
Serializable 快照读会退化为当前读，每一次执行 SELECT 都是当前读

MVCC 介绍

MVCC（Multi Version Concurrency Control，多版本并发控制）：为同一行数据维护多个历史版本，让读操作（快照读）不需要加锁就能读到合适的版本，从而实现读写互不阻塞。

MVCC 的实现依赖三部分：行记录的隐藏字段、undo log 版本链、ReadView（读视图）

实现原理

三个隐藏字段

字段名 作用
DB_TRX_ID 最近修改事务 ID，用于记录最后一次修改该记录的事务 ID
DB_ROLL_PTR 回滚指针，指向这条记录的上一个版本，用于配合 undo log
DB_ROW_ID 隐藏主键，如果表结构没有主键，才会生成该隐藏字段

如何查看：找到对应表的 .ibd 文件，执行 ibd2sdi 表名.ibd 命令（ibd2sdi 是 MySQL 自带的解析工具）

undo log

前面提到过，在事务结束时，并不会立即删除 undo log，因为 undo log 可能用于 MVCC

执行 INSERT 语句而产生了 undo log，只有在回滚时才会使用，因为在事务结束时会立即删除，而 UPDATE 和 DELETE 语句产生的 undo log，不仅在回滚时使用，在快照读时也会使用，因此不会立即删除

undo log 版本链，用于记录多个事务修改同一记录时，该记录的各个版本

readview

ReadView（读视图）：快照读执行时，MVCC 依据它来判断该读哪些版本的数据。ReadView 生成的那一刻，会记录下系统中所有活跃事务（已开始但尚未提交的事务）的 ID

ReadView 中包含了四个核心字段：

字段 含义
m_ids 活跃事务ID的集合
min_trx_id 最小活跃事务ID
max_trx_id 预分配事务ID，即当前最大事务ID + 1
creator_trx_id ReadView 创建者的事务ID

当快照读执行时，如何判断能够访问undo log 版本链中的哪个版本：

  1. trx_id = creator_trx_id：可以访问
  2. trx_id < min_trx_id：可以访问
  3. trx_id > max_trx_id：不可以访问
  4. min_trx_id <= trx_id <= max_trx_id 且 trx_id 不存在于 m_ids：可以访问

假设存在如下事务:

事务 2 事务 3 事务 4 事务 5
BEGIN BEGIN BEGIN BEGIN
UPDATE（age -> 3） SELECT
COMMIT
UPDATE（name -> A3）
SELECT
COMMIT
UPDATE（age -> 10）
SELECT
SELECT
COMMIT

根据该事务执行顺序会生成如下的 undo log 版本链

地址 id age name DB_TRX_ID DB_ROLL_PTR
30 10 A3 4 0x0003
0x0003 30 3 A3 3 0x0002
0x0002 30 3 A30 2 0x0001
0x0001 30 30 A30 1 null

Read Commit 隔离级别下，每一次执行快照读都会生成一个 ReadView

  1. 事务 5 第一次执行 SELECT 时生成一个 ReadView，各字段值为：m_ids: [3, 4, 5]、min_trx_id: 3、max_trx_id: 6、creator_trx_id: 5
  2. 事务 5 第二次执行 SELECT 时又生成一个新的 ReadView，此时事务 3 已提交，各字段值为：m_ids: [4, 5]、min_trx_id: 4、max_trx_id: 6、creator_trx_id: 5
  3. 根据判断规则，第一个 SELECT 沿版本链找到地址为 0x0002 的数据（age=3, name=A30）
  4. 第二个 SELECT 找到地址为 0x0003 的数据（age=3, name=A3），两次查询结果不一致——这就是 RC 下每次查询都重新生成 ReadView 导致的不可重复读

Repeatable Read 隔离级别下，只有第一次执行快照读会生成一个 ReadView

  1. 事务 5 第一次执行 SELECT 时会生成一个 ReadView，各字段的值为：m_ids : [3, 4, 5], min_trx_id: 3, max_trx_id: 6, creator_trx_id: 5
  2. 事务 5 第二次执行不会生成新的 ReadView，复用第一个生成的 ReadView，从而实现可重复读
  3. 由于两次查询复用同一个 ReadView，第一个和第二个 SELECT 都会查询到地址为 0x0002 的数据，结果一致——实现可重复读

总结

  1. 逻辑存储结构：表空间、段、区、页、行
  2. 架构：内存结构、磁盘结构
  3. 事务原理：原子性（undo log）、持久性（redo log）、一致性（undo log + redo log）、隔离性（锁 + MVCC）
  4. MVCC：多版本并发控制，三个隐藏字段、undo log 版本链、readview

概述主从复制：准备两台（或多台）服务器，分别安装 MySQL，一台作为主数据库（Master），一台作为从数据库（Slave）。当主库上发生数据变更时，主库会把这些操作记录到二进制日志（binlog）中，从库拉取 binlog 并重新执行，从而把主库上的操作同步到从库，保证主从数据一致。 一台主数据库可以挂多台从数据库；而一台从数据库也可以作为更下游数据库的”主库”，形成级联结构。 主从复制的作用： 高可用：主库宕机时，从库可以顶上，避免服务中断 读写分离：把查询压力分摊到从库，降低主库的访问压力 备份安全：在从库上执行备份，不影响主库的读写性能 原理前面提到，主从复制依赖二进制日志（binlog）实现：主库上所有对数据有影响的操作都会被记录到 binlog。 复制过程可以概括为三步： 主库把数据变更写入二进制日志 从库的 I/O 线程（IOThread）连接主库，拉取主库的 binlog，写入从库本地的中继日志（Relay log） 从库的 SQL 线程（SQLThread）读取中继日志并重新执行，把主库的操作在从库上重放一遍 搭建 准备两台服务器，分别安装 MySQL...
