资源操作

Java 提供了标准的 java.net.URL 类以及针对各种 URL 前缀的标准处理程序。但不幸的是，对于底层资源的访问来说，这些都还不够用。例如，没有标准的 URL 实现可用于访问需要从类路径或相对于 ServletContext 获取的资源。虽然可以为专用的 URL 前缀注册新的处理程序（类似于现有的 http: 等前缀的处理程序），但这通常非常复杂，而且 URL 接口仍然缺少一些理想的功能，例如检查所指向的资源是否存在的方法。

Spring 的 Resource 接口位于 org.springframework.core.io 包中，旨在成为一个更强大的接口，用于抽象对底层资源的访问。

Resource

Resource 只是一个接口，提供了以下的方法，我们在使用时要使用其实现类

ResourceLoader

上面的实例中，我们每获取一种不同类型的资源，就要使用对应的实现类，比较麻烦，而 ResourceLoader 解决了这个问题。

ResourceLoader 也是一个接口，我们可以通过其实现类的实例对象来调用 getResource 方法获取 Resource 对象。根据传入的 path 前缀不同，返回的 Resource 对象也不同，让你能在代码中不硬编码资源的读取方式——只写一个路径字符串，框架自动帮你选对实现。

前缀 返回的 Resource 实现
classpath: ClassPathResource
file: FileSystemResource
http: / https: UrlResource
无前缀 取决于 ApplicationContext 类型

注意：ApplicationContext 本身就是 ResourceLoader，这是最容易被忽略的一点。Spring 的 ApplicationContext 继承了 ResourceLoader，所以你在任何能拿到 ApplicationContext 的地方，都能直接加载资源。

ResourceLoaderAware

上面提到 ApplicationContext 本身就是 ResourceLoader，因此在 Spring 项目中，99% 的场景下我们都可以直接通过自动注入 ApplicationContext 的方式来获取资源。

但是，如果我们无法获取 ApplicationContext 该怎么办？ResourceLoaderAware 接口提供了一个 void setResourceLoader(ResourceLoader resourceLoader) 方法。项目启动时，ApplicationContext 会调用该方法并把自身传入，因此我们只需创建一个类实现 ResourceLoaderAware 接口，在 setResourceLoader 方法中保存传入的 ResourceLoader 即可。
