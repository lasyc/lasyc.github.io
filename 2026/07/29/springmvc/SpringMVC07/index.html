RESTful 风格

RESTful 风格 是一种基于 HTTP 协议的设计风格，它通过 URL 来表示资源，通过 HTTP 方法来表示对资源的操作

资源

在一个服务器中，万物皆是资源，比如一个 html 文件、一个图片、一个视频、一个用户、一个订单等等每一个资源都有一个唯一的 URL 来表示

资源的表述

资源的表述指的就是资源的表现形式，比如：HTML、JSON、XML 等等不同的表述形式可以通过 HTTP 的 Accept 请求头来进行协商

状态转移

状态转移指的是客户端通过 HTTP 方法来对资源进行操作，比如：GET、POST、PUT、DELETE 等等不同的 HTTP 方法表示不同的操作

实现思路

在 HTTP 请求中，存在多种请求方式，分别为: GET、POST、PUT、DELETE、HEAD、OPTIONS、PATCH、TRACE、CONNECT 等等

但是浏览器端只支持 GET 和 POST 两种请求方式，所以在浏览器端无法直接使用 PUT 和 DELETE 请求方式，不过后边学习前端框架时，会使用 Ajax 来实现 PUT 和 DELETE 请求方式

实际上，常用的请求方式只有 GET、POST、PUT、DELETE 四种，其他的请求方式很少使用而这四种请求方式也分别对应了增删改查 四种操作

请求方式 对应操作
GET 查询
POST 新增
PUT 修改
DELETE 删除

在此基础上，我们针对同一个资源，使用不同的请求方式来实现不同的操作，从而实现 RESTful 风格

在前边我们简单了解过 RESTful，当时局的例子是，将请求参数作为 URL 的一部分来传递，比如：在 Controller 中通过 RequestMapping 注解定义 URL 模板 /user/{id}，此时如果我们要查询 id 为 1 的用户信息，那么请求 URL 就是 /user/1，而不是 /user?id=1，这就是 RESTful 风格的体现

那么，我们就可以认为 /user/1 这个 URL 就是一个资源，当我们对这个 URL 使用 GET 请求时，表示查询 id 为 1 的用户信息，其他请求方式同理，以此来实现根据不同的请求方式，对同一个资源进行不同的操作，从而实现 RESTful 风格

请求方式 URL 对应操作
GET /user/1 查询 id 为 1 的用户信息
POST /user 新增
PUT /user/1 修改 id 为 1 的用户信息
DELETE /user/1 删除 id 为 1 的用户信息

HiddenHttpMethodFilter

上边的代码示例没有演示 PUT 和 DELETE 请求方式的使用，但是我们可以试一下

点击按钮后会发现，控制台打印了 selectOne1，这是因为浏览器端不支持 PUT 和 DELETE 请求方式，所以当我们点击按钮时，浏览器会将请求方式改为 GET 请求方式，因此 SpringMVC 会调用 selectOne 方法，而不是 update 或 delete 方法

SpringMVC 提供了一个 HiddenHttpMethodFilter 过滤器来解决这个问题，它可以将 POST 请求方式转换为 PUT 或 DELETE 请求方式，从而实现 RESTful 风格

在 web.xml 中配置 HiddenHttpMethodFilter 过滤器

修改 HTML 代码，使用 POST 请求，并添加一个隐藏的请求参数 _method，来指定实际的请求方式SpringMVC 会根据这个参数来判断实际的请求方式，从而调用对应的方法

再次点击按钮后，控制台打印了 update1 和 delete1，这说明 SpringMVC 成功地将 POST 请求方式转换为 PUT 和 DELETE 请求方式，从而实现了 RESTful 风格

注意事项：前边涉及到编码格式的时候，已经设置了一个 CharacterEncodingFilter 过滤器，而现在又新增了一个 HiddenHttpMethodFilter 过滤器，这两个过滤器的顺序是有要求的，HiddenHttpMethodFilter 过滤器必须在编码格式过滤器之后执行，否则会出现乱码问题因为在设置编码之前禁止获取任何参数，如果将 HiddenHttpMethodFilter 设置在前边，就会执行 request.getParameter() 方法来获取 _method 参数，而此时编码格式还没有设置好，就会出现乱码问题
