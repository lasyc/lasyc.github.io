解决方法一（对象.属性名）

上述案例都只使用了一条 SQL。除此之外，我们还可以把 SQL 拆分，分别查询员工信息和对应的部门信息，这种方式称之为分步查询。

延迟加载

在上面的多对一中，我们通过分步查询解决了问题。这种方式还可以降低 SQL 之间的耦合：将一个 SQL 拆分为两个，提高了 SQL 的复用性，两个 SQL 都可以独立执行，既能查询员工信息，也能查询部门信息。

但前提是必须在 MyBatis 中开启延迟加载。开启后，执行查询员工信息的 SQL 时只会查询员工信息；当代码中调用了 emp.getDept() 来获取部门信息时，才会触发延迟加载，此时才去查询部门信息。

设置名 描述 有效值 默认值
lazyLoadingEnabled 延迟加载的全局开关。当开启时，所有关联对象都会延迟加载。 特定关联关系中可通过设置 fetchType 属性来覆盖该项的开关状态。 true | false false
aggressiveLazyLoading 开启时，任一方法的调用都会加载该对象的所有延迟加载属性。 否则，每个延迟加载属性会按需加载（参考 lazyLoadTriggerMethods)。 true | false false （在 3.4.1 及之前的版本中默认为 true）
lazyLoadTriggerMethods 指定对象的哪些方法触发一次延迟加载。 用逗号分隔的方法列表。 equals,clone,hashCode,toString

再次执行查询语句，获取结果后只使用 emp 对象的信息，可以发现只查询了员工信息；之后再去获取 dept 对象时，才会查询部门信息。

如果开启了全局延迟加载，那么所有关联查询都会延迟执行。如果某个 SQL 不希望延迟加载呢？可以通过 fetchType 单独设置加载时机。

值 加载时机
eager 立即加载
lazy 延迟加载

这里将 fetchType 设置为 eager（立即加载），即使全局开启了延迟加载，该关联查询也会立刻执行。从下面的日志可以看到，部门查询紧随员工查询执行。
