Spring Boot 自动配置原理入门

发表于2026-08-12|更新于2026-09-12|后端框架Spring Boot
|总字数:2.2k|阅读时长:10分钟|浏览量:

自动配置原理入门

在编写主程序时，我们添加了一个注解 @Spring BootApplication，深入查看该注解我们可以看到是由另外三个注解组成的：

  1. @Spring BootConfiguration
  2. @EnableAutoConfiguration
  3. @ComponentScan

引导加载自动配置类

@Spring BootConfiguration

Spring BootConfiguration 本质就是一个 Configuration

@ComponentScan

ComponentScan 用于扫包

@EnableAutoConfiguration

EnableAutoConfiguration 则是 Spring Boot 能够实现自动装配的关键

该注解也是由另外两个注解组成的：

  1. AutoConfigurationPackage
  2. @Import({AutoConfigurationImportSelector.class})
@AutoConfigurationPackage

可以看到 AutoConfigurationPackage 注解上通过 @Import 导入了一个组件，名为 AutoConfigurationPackages.Registrar

然后利用 Registrar 向容器内批量导入组件

@Import({AutoConfigurationImportSelector.class})

调用 getAutoConfigurationEntry 加载所有组件

这个 org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件就是自动配置的候选清单（注册表），专门用来声明”当前 jar 包里有哪些自动配置类”

文件位置与命名
  • 位于每个自动配置 jar 包的 META-INF/spring/ 目录下
  • 文件名是”注解的全限定名 + .imports“，即对应 @AutoConfiguration 注解
  • 第三方 starter（如 mybatis-spring-boot-starter）也可以在自己的 jar 包中提供该文件，把自己的自动配置类注册进去
工作原理
  1. 启动时 AutoConfigurationImportSelector.getAutoConfigurationEntry() 调用 getCandidateConfigurations() 收集所有候选配置类
  2. ImportCandidates.load() 通过 classLoader.getResources() 扫描 classpath 下所有 jar 包中的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  3. 汇总去重后，再经过 @Conditional 系列注解按需过滤，只装配满足条件的配置类
版本 注册方式
Spring Boot 1.x ~ 2.6 写在 META-INF/spring.factories 中（EnableAutoConfiguration=xxx 多值键）
Spring Boot 2.7 起 新增 .imports 文件（AutoConfiguration.imports），两种方式并存
Spring Boot 3.x 只支持 .imports 文件，spring.factories 中不再读取自动配置

按需开启自动配置项

但是启动时，这些候选配置类并不会全部生效，而是会经过条件注解逐个过滤。例如 AopAutoConfiguration 上使用了 @ConditionalOnBooleanProperty(name = "spring.aop.auto", matchIfMissing = true)：matchIfMissing = true 的意思是即使配置文件中没有 spring.aop.auto，也默认认为条件满足，所以 AopAutoConfiguration 一定会被加载。但它内部的 AspectJAutoProxyingConfiguration 则不同：只有当类路径下存在 org.aspectj.weaver.Advice（即引入了 AspectJ 依赖）时它才会生效；否则就加载另一个 ClassProxyingConfiguration（使用 JDK/CGLIB 动态代理）。

再比如 MultipartAutoConfiguration，这里边限制了 multipartResolver 的 Bean 名称就叫 multipartResolver

自定义修改自动配置

还有用于设置字符编码格式的 CharacterEncodingFilter，这里使用了 @ConditionalOnMissingBean 的策略进行配置，即你没配置，我就帮你配置；你配置了，我就不配置了。

并且我们可以看到 filter.setEncoding(properties.getCharset().name());，字符编码并不是通过硬编码设置的，而是读取自配置文件。

因此，我们有两种方式来修改这类自动配置：

  1. 通过 @Bean 创建一个同类型的 Bean，这样 Spring Boot 就不会帮我们配置了
  2. 修改配置文件，让 Spring Boot 加载我们的配置

最佳实践

  1. 需要使用什么组件，比如：thymeleaf
  2. 寻找对应场景的 starter,比如：spring-boot-starter-thymeleaf
  3. 查看 jar 包中的 XxxxxAutoConfig.java 配置类，比如：ThymeleafAutoConfiguration
  4. 查看对应的 XxxxxProperties.java 配置文件，比如：ThymeleafProperties
  5. 根据配置文件中的要求修改配置
  6. 如果该配置无法满足要求，使用 @Bean 自定义配置
  7. 在配置文件中添加 debug=true 来开启 Spring Boot 的 Debug 模式，它会把自动配置的加载情况打印在控制台：哪些配置类生效了、哪些没有、为什么没有生效等信息

dev-tools

参考文档

dev-tools 用于当我们修改了 Spring Boot 的任何文件时，比如代码或者配置，然后重新编译项目（快捷键 Ctrl + F9），Spring Boot 会自动重启，让新的资源生效，这不是热更新， JRebel 是真正的热更新。

Spring Boot DevTools JRebel
本质 Spring Boot 官方自带的辅助模块 第三方商业插件（收费，有试用）
实现方式 类加载器隔离 + 自动重启 字节码热替换（Hot Swap）
触发方式 重新编译（Ctrl+F9）后自动重启 保存/编译后立即替换类
应用状态 丢失（重新执行 main，从头启动） 保留（不重启 JVM）
适用场景 修改类、配置、模板后的快速重启 频繁改代码的长期开发调试
