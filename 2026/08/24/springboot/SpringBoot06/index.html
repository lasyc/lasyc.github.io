请求映射

我们可以通过 @RequestMapping 注解来将请求路径映射到对应的方法上

RESTful 风格，本着万物皆是资源的原则，在同一个请求路径中通过不同的请求方式，来访问不同的资源

  • /user(GET、DELETE、PUT、POST)

在 Spring MVC 中我们就讲过，浏览器并不直接支持 DELETE 和 PUT 请求。为此，Spring MVC 提供了 HiddenHttpMethodFilter：通过在 form 表单中添加一个隐藏字段（默认 _method），来实现 GET 和 POST 以外的请求方式。

参考文档

在 Spring Boot 中，WebMvcAutoConfiguration 自动配置类已经帮我们配置好了这个过滤器，但默认不会生效，需要通过 spring.mvc.hiddenmethod.filter.enabled=true 手动开启。

在源码中可以看到，过滤器是通过 this.methodParam 来指定隐藏字段的，默认为 _method。如果我们想修改该字段，可以自己提供一个 HiddenHttpMethodFilter 的 Bean，这样 Spring Boot 就不会再加载默认的那个了。

Spring Boot 的本质还是一个 Servlet 应用，核心则是 DispatcherServlet。通过源码可以发现，DispatcherServlet 继承自 FrameworkServlet，而 FrameworkServlet 最终又继承自 HttpServlet。

我们在学习 Servlet 时，想要实现请求的分发，就必须重写 doGet 和 doPost 方法，查看整个继承链路，可以发现在 FrameworkServlet 中重写了 doXxx 各种方法

可以看到，所有方法都指向了 processRequest 方法

可以看到 doService 才是真正的执行方法，而 doService 则是在 DispatcherServlet 中实现的

doService 又指向了 doDispatch

在此基础上，我们便可以通过自定义 HandlerMapping 来添加自己的映射规则

@RequestBody

@RequestBody 用于接收请求体中的数据，常见的有两种用法：

  1. 接收原始字符串（请求体是什么就拿到什么）
  2. 接收 JSON 数据并转为 Java 对象（实际开发中最常用）

原理简述：@RequestBody 由 RequestResponseBodyMethodProcessor 解析，底层通过 HttpMessageConverter（消息转换器）将请求体转换为目标对象。JSON 的转换由 Jackson 提供的 MappingJackson2HttpMessageConverter 完成。在 Spring Boot 中，只要引入了 spring-boot-starter-web，就已经内置了 Jackson，无需额外配置。

@RequestBody 与 @RequestParam 的区别：@RequestParam 从 URL 查询参数或表单字段中取值，@RequestBody 从请求体中取值（JSON、XML 等）

@RequestAttribute

@ModelAttribute

@ModelAttribute 有两种用法：

  1. 方法级：标注在 @Controller 的方法上，任意 handler 方法执行前会先执行该方法，并把返回值放入 Model
  2. 参数级：标注在形参上，将请求参数绑定到该对象上（也可以省略不写，Spring 默认就会自动绑定）

注意：方法级 @ModelAttribute 只对当前 Controller 生效，且每次请求都会先执行，若其他 handler 方法也使用同名的 Model 属性，可能会被影响，需留意

@MatrixVariable

@MatrixVariable 是 Spring MVC 中的一个注解，用于从 URL 路径中的矩阵变量（Matrix Variables） 里提取值。

矩阵变量是 URI 规范（RFC 3986）中的一种扩展语法，以 分号 ; 分隔，附加在路径段（path segment）上，如：/colors/red;r=255;g=0;b=0

Spring Boot 默认不会解析矩阵变量，需要通过配置开启：覆写 configurePathMatch，设置 setRemoveSemicolonContent(false)（false 表示不移除路径中的分号内容）。

实际的开发中，我们经常需要对请求参数进行校验（非空、长度、范围等），如果手动在业务代码里一个个 if 判断，代码会非常臃肿。Spring 提供了基于 Bean Validation（JSR-303） 规范的注解校验，SpringBoot 中只需引入 spring-boot-starter-validation

文件上传

SpringBoot 默认使用 StandardServletMultipartResolver 处理文件上传，无需任何额外配置（对比 SpringMVC 需要配置解析器，SpringBoot 已经自动配置好了）

多文件上传时，只需将参数类型改为 MultipartFile[] 或 List<MultipartFile>，前端表单中多个 name="file" 的 input 即可

参数处理原理

  1. 从 HandlerMapping 中找到对应的 Handler
  2. 为当前 Handler 找到对应的 HandlerAdapter（适配器）
  3. HandlerAdapter 执行对应的 Handler
  4. 调用 setHandlerMethodArgumentResolvers 设置参数解析器

我们知道 Spring 通过各种的参数解析器来解析参数，那么对于 Servlet 原生的一些参数，也有对应的解析器 ServletRequestMethodArgumentResolver

因此，我们可以直接在 handler 方法中，使用对应的参数，不需要任何注解，Spring 会帮我们自动注入

最后两个是兜底解析器：简单类型（String、Integer 等）交给 RequestParamMethodArgumentResolver，复杂类型（POJO 等）交给 ServletModelAttributeMethodProcessor

自定义对象参数绑定原理

自定义对象参数由 ServletModelAttributeMethodProcessor 解析（它继承自 ModelAttributeMethodProcessor）

绑定过程大致如下：

  1. 反射创建目标对象（BeanUtils.createInstance）
  2. 通过 ServletRequestDataBinder（继承自 WebDataBinder）绑定请求参数
  3. 绑定过程中使用 ConversionService 做类型转换（String → Integer、String → Date 等），也支持级联属性（address.province）
  4. 若参数上标注了 @Validated，绑定后还会执行数据校验（后续章节会讲到）

类型转换

默认的 ConversionService（ApplicationConversionService）已经内置了大量常用转换器，但自定义的转换规则需要我们实现 Converter、Formatter 或 GenericConverter 接口

自定义参数解析器

除了使用 Spring 提供的解析器，我们也可以实现 HandlerMethodArgumentResolver 接口来自定义解析规则

通过 addArgumentResolvers 添加的自定义解析器会排在默认解析器之前，优先匹配；如果 supportsParameter 返回 false，才会继续匹配默认解析器

注解 作用 使用场景
@PathVariable 从 URL 路径中提取参数 /user/{id}
@RequestParam 从查询参数或表单字段中取值 ?username=admin
@RequestHeader 从请求头中取值 获取 User-Agent 等

简单类型参数（String、Integer 等）走 @RequestParam 逻辑，复杂对象参数（POJO）走 @ModelAttribute 逻辑，这是 Spring 的兜底解析规则

数据响应与协商

响应 JSON

@ResponseBody 用于将方法的返回值作为响应体返回，当返回的是对象时，Spring 会通过 HttpMessageConverter 将其序列化为 JSON。在 SpringBoot 中，spring-boot-starter-web 已内置 Jackson，无需额外添加依赖（下面是最新 Jackson 3.x 的坐标，仅作了解）

@RestController = @Controller + @ResponseBody，开发中直接使用 @RestController 即可，所有方法的返回值都会尝试转为 JSON

响应 XML

@ResponseBody 除了能返回 JSON，也能返回 XML，不过需要额外做两件事：

  1. 引入 JAXB 相关依赖（Spring Boot 3.x 起已不再默认携带 JAXB）

  2. 在实体类上标注 @XmlRootElement

  3. 控制器方法通过 produces 限定产出 XML（也可以不指定，由内容协商自动决定）

原理：当客户端 Accept 头为 application/xml 时，Spring 会找到 Jaxb2RootElementHttpMessageConverter（基于 JAXB 的消息转换器）来完成对象到 XML 的序列化。引入 JAXB 依赖后，同一个接口可能既返回 JSON 又返回 XML，具体返回哪种由下边的内容协商机制决定

协商

通过获取请求头中 Accept 字段可以知道浏览器支持哪些数据格式，再根据服务器可以响应哪些数据格式，两者进行匹配，根据权重优先使用匹配的方式进行响应

三种协商方式

Spring 支持三种内容协商方式，优先级从高到低：

  1. 路径后缀：/user.json、/user.xml（Spring Boot 默认关闭，避免后缀伪装攻击）
  2. 请求参数：/user?format=xml（默认关闭，需要手动开启）
  3. Accept 请求头：Accept: application/xml（默认方式）

只要方法上标注了 @ResponseBody，返回值就会交给 RequestResponseBodyMethodProcessor 处理，通过 HttpMessageConverter 转为 JSON 响应

返回值解析器原理

处理流程大致如下：

  1. 目标方法执行完毕，拿到返回值（如 User 对象）
  2. RequestResponseBodyMethodProcessor 判断方法上是否有 @ResponseBody 注解，有则处理
  3. 遍历 HttpMessageConverter 列表，找到支持该类型转换的转换器（如 MappingJackson2HttpMessageConverter）
  4. 通过转换器将对象序列化为 JSON，写入响应体，同时设置 Content-Type: application/json

该处理器与请求参数中的 @RequestBody 是同一个 RequestResponseBodyMethodProcessor，只是处理方向相反：一个是”读”（请求体 → 对象），一个是”写”（对象 → 响应体）

自定义 HttpMessageConverter

注意：前面”类型转换”章节的 Converter 处理的是单个参数（如 String → Date、String → 枚举），而 HttpMessageConverter 处理的是整个消息体（@RequestBody / @ResponseBody 的序列化与反序列化），两者是不同层面的东西，别混淆。

如果默认的 JSON/XML 转换器不满足需求，我们可以实现 HttpMessageConverter 接口来自定义消息转换规则
