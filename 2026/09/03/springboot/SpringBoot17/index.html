Spring Boot 定制化原理

发表于2026-09-03|更新于2026-09-12|后端框架Spring Boot
|总字数:2.4k|阅读时长:8分钟|浏览量:

Spring Boot 的自动配置帮我们省去了大量样板代码，但自动配置提供的只是”通用默认值”。真实项目中我们常常需要在此基础上做调整：改端口、关模板缓存、给 JSON 统一日期格式、加拦截器……这些”在默认配置之上做修改”的操作，就是定制化。

只有理解了定制化的原理，才能既享受自动配置的便利，又不会在需要调整时无从下手。本篇基于之前学过的知识，把常见的定制化方式梳理一遍，并分析它们背后的统一原理。

定制化的常见方式

  1. 通过配置文件来定制化，即在 application.properties 或 application.yml 中进行配置。
  2. 通过配置类来定制化，即通过 @Configuration 注解来标注一个配置类，然后在配置类中定义 Bean 来进行定制化。
  3. 通过 XxxxCustomizer 来定制化，即通过实现 XxxxCustomizer 接口来进行定制化。
  4. 创建配置类实现 WebMvcConfigurer 接口，重写其中的方法来定制化。
  5. 在配置类上添加 @EnableWebMvc，全面接管 Web 容器，Spring 帮我们做的配置全部失效。

下面逐一展开。第 5 种属于”极端手段”，通常不推荐，但理解了它，你对 Spring Boot 的自动配置边界会有更清晰的认识。

1. 通过配置文件定制化

这是最常用、也最简单的方式。Spring Boot 把每个场景的默认值都抽取成了对应的 XxxProperties 类（例如 ServerProperties、ThymeleafProperties、MultipartProperties），并通过 @ConfigurationProperties 与配置文件绑定。

上面这段配置分别对应：

配置项 绑定的 Properties 作用
server.port ServerProperties 修改端口号
spring.thymeleaf.cache ThymeleafProperties 关闭模板缓存
spring.servlet.multipart.* MultipartProperties 修改文件上传大小限制

在 IDEA 中写配置时，只要输入 spring. 或 server. 就会弹出提示，因为这些类都在 classpath 中，IDE 能直接读取到它们的元数据。

如果某个场景连 XxxProperties 都没有提供（比如第三方 starter 没写属性类），那我们也可以仿照 @ConfigurationProperties 的做法，自己写一个配置类来承载自定义配置项。

2. 通过配置类 + @Bean 定制化

当”改属性”满足不了需求时，我们可以直接提供一个同类型的 Bean，把 Spring Boot 自动配置的那个”顶掉”。

为什么这样做就能生效？因为在 自动配置 篇中我们看过，Spring Boot 在注册默认组件时大量使用 @ConditionalOnMissingBean——**”容器里没有，我才帮你配；你自己配了，我就不配了”**。

由于我们的 WebConfig 是用户配置类，会在自动配置类之前被处理，所以当我们提供了 HiddenHttpMethodFilter 后，自动配置里的那个就因条件不满足而不再创建。

判断技巧：想覆盖某个默认组件，先看它对应的自动配置类（XxxAutoConfiguration）里注册该 Bean 的方法上有没有 @ConditionalOnMissingBean，有，就可以直接用 @Bean 覆盖。

3. 通过 XxxxCustomizer 定制化

有些组件不是”单个 Bean”，而是”构建过程比较复杂”，直接整体替换成本太高。这时 Spring Boot 提供了 XxxCustomizer 这类回调接口：在自动配置构建默认对象时，会把容器中所有实现该接口的 Bean 收集起来，依次调用，让我们在构建过程中”插一脚”。

4. 通过 WebMvcConfigurer 定制化

Spring MVC 相关的功能（拦截器、静态资源、跨域、视图控制器、消息转换器等）在 Spring Boot 中统一由 WebMvcAutoConfiguration 自动配置。要修改这些行为，官方推荐的方式是写一个配置类实现 WebMvcConfigurer 接口，按需重写其中的方法——接口里的方法全部是默认空实现，用哪个重写哪个即可。

它之所以能生效，是因为 WebMvcAutoConfiguration 内部实际采用的是”委托”模式：它会收集容器中所有 WebMvcConfigurer 实现类，在构建各个 MVC 组件（如 RequestMappingHandlerAdapter、ResourceHandlerRegistry 等）时逐一回调我们的重写方法，把我们的配置合并进去。

关键点：这里不要加 @EnableWebMvc，只实现 WebMvcConfigurer 即可，这样我们的配置是在默认配置之上做”增量修改”。

5. @EnableWebMvc：全面接管

如果我们在配置类上加上 @EnableWebMvc，情况就完全不同了：它会导入 DelegatingWebMvcConfiguration，而 WebMvcAutoConfiguration 上有 @ConditionalOnMissingBean(WebMvcConfigurationSupport.class) 这样的条件——一旦发现 MVC 的基础配置类被导入，Spring Boot 帮我们做的整套 Web MVC 默认配置就全部失效，静态资源映射、欢迎页、视图解析器、默认消息转换器等都需要我们自己配回来。

这意味着从一个”开箱即用”的框架变成了”框架只提供地基，其余全部自己盖”，工作量会大很多，也容易踩坑。因此**一般情况下不要使用 @EnableWebMvc**，第 4 种方式（实现 WebMvcConfigurer）已经能满足绝大多数定制需求。

原理分析

为什么”用户配置”总能赢过”自动配置”

把上面 5 种方式放在一起看，会发现它们的底层都指向同一个事实：自动配置永远让位于用户配置。

这要从自动配置类的加载时机说起。Spring Boot 启动时，主程序所在包下的用户配置类（@Configuration）会先被扫描注册；而 AutoConfiguration.imports 里列出的自动配置类，则由 AutoConfigurationImportSelector 在用户配置处理完之后才统一导入（详见自动配置篇）。

正因为自动配置类看得见用户已经定义的 Bean，它才能用 @ConditionalOnMissingBean 做出”你不配我才配”的退让。这就是方式二（@Bean 覆盖）能生效的根本原因。

定制化的核心三板斧

手段 解决的问题 底层机制
配置文件（application.yml） 调整参数、开关 @ConfigurationProperties 属性绑定到 XxxProperties
@Bean 提供同类型 Bean 整体替换某个默认组件 自动配置上的 @ConditionalOnMissingBean 条件失效
XxxCustomizer / WebMvcConfigurer 在默认构建/装配过程中做增量修改 自动配置收集容器中的回调实现并依次调用

遇到”想改却不知道在哪改”怎么办

可以按下面这个顺序排查：

  1. 想改的东西属于哪个场景？找到对应的 spring-boot-starter-xxx
  2. 查该场景的自动配置类 XxxAutoConfiguration，看它 @Import / 注册了哪些组件、读取哪个 XxxProperties
  3. 能改属性就先改属性（方式一）
  4. 属性不够用，看目标 Bean 上有没有 @ConditionalOnMissingBean，有就 @Bean 覆盖（方式二）
  5. 组件构建复杂、不想整体替换，看有没有对应的 XxxCustomizer（方式三）
  6. 是 Spring MVC 的行为，优先实现 WebMvcConfigurer（方式四）
  7. 以上都不行，再考虑 @EnableWebMvc 全面接管（方式五）

总结一句话：Spring Boot 的自动配置 = “提供合理的默认值 + 留出定制入口”。默认值永远让位于用户配置，理解这一点，定制化就不再是死记硬背，而是一套有迹可循的方法。
