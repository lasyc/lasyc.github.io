Profile

为了方便多环境适配,Spring Boot 简化了 profile 功能

Profile 功能

在实际开发中，会存在多种环境，比如：开发环境（development）、测试环境（test）、生产环境（production）

因此我们可以将配置文件分为：application-dev.yaml、application-test.yaml 等

而 application.yaml 是默认被加载的

创建 application-dev.yaml 文件，并修改端口为 8081

在 application.yaml 中声明当前环境为 dev

启动项目后发现，访问 8081 端口才能访问服务，证明 application-dev.yaml 生效了，当然 application.yaml 中的配置也会生效，只不过如果两者配置冲突，则以 dev 为准

在项目打包后，我们仍可以在启动项目时，通过传入配置参数来修改环境

@Profile

Spring Boot 还提供了一个注解 @Profile，用于在不同的环境下装配不同的配置类

声明 Druid 数据源只有在 prod 环境下才生效

Profile 组

可以将多个 Profile 分组，指定当前组之后可以让其中所有的配置文件都生效

外部配置

在前面学习的时候，凡是有可能需要调整的配置项，我们都会把它抽取到配置文件中，而不是硬编码在代码里，这种把配置从代码中分离出来的做法就叫外部化配置

在 Spring Boot 中，一个 application.yaml 基本就可以满足我们的使用

配置文件位置

Spring Boot 启动时，会去如下路径查找配置文件

  1. classpath 根路径
  2. classpath 根路径下 config 目录
  3. jar 包所在目录
  4. jar 包所在 config 目录
  5. /config 子目录（Linux）

自定义 Starter

Spring Boot 启动时会扫描所有 jar 中的自动配置声明文件，把里面声明的自动配置类作为候选。那么我们自己写一个 starter，让使用方只需引入一个坐标就能自动拥有某个功能，一般需要三步：

  1. 编写自动配置模块：提供 XxxAutoConfiguration 自动配置类和 XxxProperties 属性绑定类
  2. 在自动配置模块中新建声明文件，把自动配置类注册进去
  3. 编写 starter 聚合模块：在 pom 中引入自动配置模块，供别人引用

早期写法是在 META-INF/spring.factories 文件中声明 org.springframework.boot.autoconfigure.EnableAutoConfiguration=...，该方式从 Spring Boot 3.x 起已被移除，现在的声明文件统一放在 META-INF/spring/ 下（详见下文）。

下面以编写一个 hello-spring-boot-starter（引入后自动装配一个 HelloService）为例。

1. 自动配置模块（autoconfigure）

属性绑定类 HelloProperties

@ConfigurationProperties(prefix = "hello") 会把配置文件中的 hello.* 绑定到该类的属性上，name 的默认值是 world（没配置时使用）。

功能类 HelloService

starter 真正提供的功能，只是一个普通类，不依赖 Spring：

自动配置类 HelloAutoConfiguration

  • @AutoConfiguration：自动配置类专用注解（内部组合了 @Configuration），Spring Boot 2.7+ 提供
  • @EnableConfigurationProperties(HelloProperties.class)：把属性绑定类注册为 Bean，并开启属性绑定
  • @ConditionalOnClass(HelloService.class)：classpath 中存在 HelloService 时才加载本配置类（即引入了本模块时）
  • @ConditionalOnMissingBean：容器中还没有 HelloService 时才创建这个 Bean，允许使用方自己定义覆盖

注册自动配置类

在自动配置模块的 src/main/resources/META-INF/spring/ 目录下新建文件 org.springframework.boot.autoconfigure.AutoConfiguration.imports，把自动配置类的全限定类名写进去（每行一个）：
