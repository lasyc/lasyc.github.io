Spring Boot 自动装配与内嵌容器

发表于2026-09-07|更新于2026-09-12|后端框架Spring Boot
|总字数:2.8k|阅读时长:12分钟|浏览量:

自动装配原理

refresh 第 5 步解析启动类时，会碰到 @SpringBootApplication 上的 @EnableAutoConfiguration，自动装配的入口就在这。

入口：@EnableAutoConfiguration

AutoConfigurationImportSelector 是一个 DeferredImportSelector。Deferred（延迟）的意思是：它不会在解析到 @EnableAutoConfiguration 时立刻导入，而是等我（用户）自己写的所有 @Configuration、@Bean、@ComponentScan 都处理完之后，再统一导入自动配置类。这样就保证了”自定义优先，自动配置兜底“：我注册的 @Bean 在先，自动配置里那些 @ConditionalOnMissingBean 一看容器里已经有了，就自动让位——13 篇定制化能生效，靠的就是这个顺序。

两层条件过滤

读进来的 100 多个自动配置类显然不会全部生效，能不能生效靠 @Conditional 系列注解决定。整个过程分两层：

第一层（粗筛）：不加载类就过滤。 AutoConfigurationImportFilter（实现有 OnClassCondition、OnWebApplicationCondition）拿到的是全限定类名，它用 ASM 直接读 class 文件的元数据做判断，类都没进 JVM，成本极低。比如没引 Redis 依赖时，RedisAutoConfiguration 在这一层就被剔掉了。

第二层（细筛）：当配置类解析时评估 @Conditional。 通过粗筛的类会被当成普通 @Configuration 处理，这时它身上的 @Conditional 才由 Spring 的 ConditionEvaluator 真正评估。拿 DataSourceAutoConfiguration 举例：

把常用的条件注解整理成速查表：

注解 生效条件
@ConditionalOnClass / @ConditionalOnMissingClass classpath 中存在 / 不存在某个类
@ConditionalOnBean / @ConditionalOnMissingBean 容器中已有 / 没有某个 Bean
@ConditionalOnProperty 配置文件中存在指定属性且值匹配
@ConditionalOnWebApplication 当前是 Web 应用
@ConditionalOnExpression SpEL 表达式为 true

自动配置类之间的顺序

自动配置类彼此也有依赖（比如 RedisAutoConfiguration 需要先有连接工厂的自动配置），顺序由三个注解控制，Boot 会收集起来统一排序：

  • @AutoConfigureBefore(Xxx.class)：在 Xxx 之前
  • @AutoConfigureAfter(Xxx.class)：在 Xxx 之后
  • @AutoConfigureOrder(n)：数字越小越靠前

怎么确认哪些自动配置生效了

想确认到底哪些自动配置生效了，我常用两种办法：

  1. 启动时加 --debug 或在 application.yaml 里写 debug: true，控制台会打印 Positive matches（生效的自动配置及原因）和 Negative matches（未生效的及原因）
  2. 引入 Actuator 后访问 /actuator/conditions 端点（16 篇端点表格里的 conditions 就是它）

内嵌 Web 容器的启动

回到 refresh 第 9 步 onRefresh()。AnnotationConfigServletWebServerApplicationContext 的父类 ServletWebServerApplicationContext 覆写了它：

TomcatServletWebServerFactory 是哪里来的？由 ServletWebServerFactoryAutoConfiguration 自动配置提供（类上标着 @ConditionalOnClass(Tomcat.class)，只要引了 spring-boot-starter-tomcat 就生效）；server.port、server.servlet.context-path 这些配置则通过 ServerProperties（@ConfigurationProperties(prefix = "server")）绑到工厂上。

注意：getWebServer(...) 只是创建了 Tomcat 对象，真正 start() 发生在 refresh 第 12 步 finishRefresh()——容器会启动一个 WebServerStartStopLifecycle，由它调用 webServer.start()，到这一步 Tomcat 才真正监听端口、开始接受请求。DispatcherServlet 则由 DispatcherServletAutoConfiguration 提供的 Bean 注册进 ServletContext，交给内嵌容器统一管理。

一句话记下来：内嵌容器不是外部装好的，而是容器刷新过程中由 Boot 的自动配置 + 模板方法现场创建并启动的。这也解释了为什么依赖里带上 spring-boot-starter-tomcat，什么都不配就能在 8080 端口跑起来。

源码跟到这里，整条链路基本就串完了。有一点体会：光读记不住，我是实际打断点走了一遍才真正串起来的，比较值得断的位置是 SpringApplication 构造器、run()、AbstractApplicationContext.refresh()、ConfigurationClassPostProcessor.processConfigBeanDefinitions、AutoConfigurationImportSelector.getAutoConfigurationEntry、ServletWebServerApplicationContext.createWebServer() 这几处。走完再回头看 13 篇的定制化和 17 篇的自定义 Starter，会发现它们其实都是在这条主链路的某个环节上做文章：定制化是替换链路上的 Bean，自定义 Starter 是往 AutoConfiguration.imports 里加一行自己的配置类。

自定义事件监听器

前面 run() 里那套 RunListener 阶段回调 + 事件广播，光看源码不过瘾，我写了几个自定义组件实际跑了一把，验证它们到底在哪个时机被触发。启动链路上能让我们”插一脚”的接口主要有五个：

  1. ApplicationContextInitializer —— refresh 之前执行，能对刚创建的 ApplicationContext 动手脚
  2. ApplicationListener —— 监听容器发布的各种 ApplicationEvent
  3. ApplicationRunner —— 容器刷新完成后执行，入参是解析好的 ApplicationArguments
  4. CommandLineRunner —— 同上，入参是原始 String[]
  5. SpringApplicationRunListener —— 站在整个 run() 最外层，从 starting 到 ready 全程回调

注册方式分两类：前两个和最后一个必须通过 spring.factories 注册（容器还没起来，@Component 扫不到它们），两个 Runner 是普通 Bean，直接 @Component 就行。下面逐个写实现。

日志里能对上前面的时序，记几个观察点：

  • starting → environmentPrepared → contextPrepared → contextLoaded → started → ready 六个阶段和 run() 源码一一对应，Banner 打印、容器创建、Tomcat 启动都能在日志里找到落点
  • CustomApplicationListener 在 Banner 打印之前就输出了两次——那是 starting、environmentPrepared 两个早期事件。spring.factories 注册的监听器从 run 一开始就能收到事件；而普通 @Component Bean 要等容器 refresh 时才会被实例化，注定错过早期事件（这正是它俩必须走 spring.factories 的原因）
  • Runner 的执行点在 “Started StudyApplication” 日志之后、ready 之前；两个 Runner 顺序固定：ApplicationRunner 先、CommandLineRunner 后
  • 跟完这一路，五种接口其实是三层东西：RunListener 在 run() 最外层全程回调；Initializer 在 refresh 之前插手；Listener 靠事件被动触发；两个 Runner 是刷新完成后跑业务代码的入口
