跨域

项目搭建完成后，发送请求时会报错如下，这是因为还没有配置跨域

跨域一般发生在前后端分离的场景，因为前后端都是独立的服务，比如前台运行在 http://localhost:5174 上，而后台运行在 http://localhost:8080 上，当 协议、域名、端口 三者中任意一个不一致时，就会触发浏览器的安全机制同源策略（Same-Origin Policy），从而出现上面的报错

Spring Boot 解决跨域

CORS，全称为“跨域资源共享”（Cross-Origin Resource Sharing），是一种机制，它使用额外的 HTTP 头来告诉浏览器允许一个网页从另一个域（不同于该网页所在的域）请求资源。这样可以在服务器和客户端之间进行安全的跨域通信。

Spring Boot 支持三种常用的 CORS 配置方式：

  1. 全局配置：实现 WebMvcConfigurer#addCorsMappings
  2. 控制器配置：在类上标注 @CrossOrigin
  3. 接口配置：在方法上标注 @CrossOrigin

注意类名不要和上面的 WebMvcConfigurer 配置类重名，这两种配置是二选一的关系

http.cors(Customizer.withDefaults()) 会自动去容器中查找名为 corsConfigurationSource 的 bean，所以不需要再把 CorsConfigurationSource 注入成方法参数；如果想显式指定，也可以写成 http.cors(cors -> cors.configurationSource(corsConfigurationSource))

区别

本质是同一套实现的两个挂载点

Spring Boot 和 Spring Security 的跨域并不是两套不同的技术，底层用的都是同一个 CorsConfiguration 和同一个 DefaultCorsProcessor，区别只在于配置挂载的位置不同

Spring Boot 跨域 Spring Security 跨域
配置入口 WebMvcConfigurer#addCorsMappings、@CrossOrigin http.cors(...) + CorsConfigurationSource
底层实现 CorsConfiguration / DefaultCorsProcessor 同一套
挂载点 AbstractHandlerMapping，位于 DispatcherServlet 内部 CorsFilter，位于 Security 过滤器链上
生效时机 晚（请求已经进入 DispatcherServlet） 早（早于认证授权，还没进入 DispatcherServlet）
预检 OPTIONS 需要一路走到 DispatcherServlet 才会被处理 在 CorsFilter 中直接被返回

为什么引入 Spring Security 之后必须用 Security 的跨域

因为浏览器的**预检请求（OPTIONS）不会携带 Cookie**，如果只配置了 Spring Boot 的跨域而没有开启 http.cors()，预检请求会先被 Security 的过滤器拦下，此时没有任何身份凭证，一旦存在 authenticated() 之类的鉴权规则，就会被判定为未认证而直接返回 401 / 403，Access-Control-Allow-* 响应头根本没有机会被写入

开启 http.cors() 之后，CorsFilter 在预检请求处会直接短路返回

所以官方文档中有一句很直白的描述：CORS must be processed before Spring Security

两者可以共存吗

可以，DefaultCorsProcessor 在真正处理之前会先检查响应头

也就是说谁先写入 Access-Control-Allow-Origin，谁生效，后处理的会自动跳过，因此不会出现重复响应头

但由于 Security 的 CorsFilter 排在 DispatcherServlet 之前，实际效果是 Security 的那份配置说了算，MVC 的那份在普通请求上基本被短路掉了。如果两边配置不一致，就会出现“改了 addCorsMappings 却不生效”的情况，这不是 bug，而是由顺序决定的

优先使用哪个

结论是：只要引入了 Spring Security，就统一使用 Security 的跨域配置

  1. 显式提供一个名为 corsConfigurationSource 的 CorsConfigurationSource bean，并配上 http.cors(Customizer.withDefaults())
  2. 不要再配置 addCorsMappings 或 @CrossOrigin，避免存在两份配置而难以排查

http.cors() 查找配置源的顺序依次为：显式调用的 configurationSource(...) → 名为 corsFilter 的 bean → 名为 corsConfigurationSource 的 bean → MVC 提供的 mvcHandlerMappingIntrospector

注意：在较新的版本中（Spring Framework 7.1 起）HandlerMappingIntrospector 已被移除，Security 无法再从 MVC 隐式借用跨域配置，因此“显式声明 CorsConfigurationSource”是跨版本都更可靠的做法

字段差异

字段 Spring Boot（CorsRegistry） Spring Security（CorsConfiguration）
允许的源 allowedOrigins(...) setAllowedOrigins(List<String>)
允许的方法 allowedMethods(...) setAllowedMethods(List<String>)
允许的请求头 allowedHeaders(...) setAllowedHeaders(List<String>)
携带凭证 allowCredentials(true) setAllowCredentials(true)
预检缓存时间 maxAge(3600) setMaxAge(3600L)

CorsRegistry 的链式调用内部也是先构造出一个 CorsConfiguration，只是省去了逐个 set 的步骤，字段含义完全一致

需要注意的是 CorsRegistry#maxAge 接收的是基本类型 long，而 CorsConfiguration#setMaxAge 接收的是包装类型 Long，所以后者要写成 3600L

如果前端需要携带 Cookie 或 Token 发起请求，两边都必须开启 allowCredentials，并且此时允许的源不能写成 "*"（Spring 会直接抛出 IllegalArgumentException），必须写具体的源或者改用 allowedOriginPatterns，否则浏览器同样会拦截响应
