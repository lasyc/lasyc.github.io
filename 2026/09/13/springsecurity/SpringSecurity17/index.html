Spring Security 禁用 Session

发表于2026-09-13|更新于2026-09-13|后端框架Spring Security
|总字数:2.2k|阅读时长:7分钟|浏览量:

传统 Session

在前面使用 Thymeleaf 的场景下，我们每次登录后台服务都会创建一个 Session，并且在响应时通过 Set-Cookie 把 JSESSIONID 写进浏览器的 Cookie；之后的每次请求都会自动携带这个 JSESSIONID，服务端据此就能知道用户的登录状态为已认证，从而允许其访问受保护的资源。

但是在前后端分离场景下，Session 虽然还能继续使用，却比较鸡肋：前端与后端通常不同源，想在跨域下携带 Cookie 要额外做不少配置（后端 config.setAllowCredentials(true) 只是其中一环），而且浏览器对跨站 Cookie 的限制也越来越严；后端多实例部署时，登录请求落在 A 服务器、后续请求落到 B 服务器，B 并不认识 A 发出的 JSESSIONID，就会判定用户未认证；此外像微信小程序、APP 这类客户端本身并没有浏览器 Cookie 机制。这几点会在下一节展开。

因此，在前后端分离的场景下，更推荐禁用 Session，不再在服务端保存用户状态：用户登录认证通过后，服务端根据用户信息生成一个唯一的令牌 Token 返回给前端；前端后续请求在请求头中携带该 Token，服务端通过解析 Token 重新确定用户的身份和权限。这种做法称为无状态（stateless）。

至于 Token 如何生成，又会涉及到另一个知识点 JWT，会在下一章节讲述。

禁用 Session

默认情况下 Session 是怎么被用上的

Spring Security 默认的会话策略是 SessionCreationPolicy.IF_REQUIRED；共享的 SecurityContextRepository 默认是一个 DelegatingSecurityContextRepository，内部同时委托给 RequestAttributeSecurityContextRepository 和 HttpSessionSecurityContextRepository。也就是说：

  • 认证成功后，认证过滤器（如 UsernamePasswordAuthenticationFilter）会调用 SecurityContextRepository#saveContext()，把 SecurityContext 同时写进当前请求的 request attribute 和 HttpSession
  • 响应头里会多一个 Set-Cookie: JSESSIONID=xxx
  • 浏览器后续请求会自动带上这个 Cookie，服务端再从 Session 里把认证信息恢复出来

这套机制在服务端渲染的项目里非常自然，但在前后端分离下就变成了负担。

为什么推荐禁用

前后端分离的接口本身就是无状态的：凭证由前端自己保存（比如 Token 放在 Authorization 请求头里），每次请求都带着走，服务端不需要靠 Cookie 里的 JSESSIONID 去回想”这个人是谁”。

如果不禁用，会带来下面几个问题：

  1. 水平扩展要额外处理会话共享
    Session 默认存在单个 JVM 的内存里，多实例部署时要么做会话粘滞（sticky session），要么做 Session 复制 / 集中存储（比如 Redis），否则请求落到另一个实例上就”掉登录”。

  2. 跨域场景下 Cookie 很麻烦
    前后端不同源时，Cookie 需要 withCredentials、SameSite、Secure 等一系列配合，浏览器对跨站 Cookie 的限制也越来越严；而 Token 放在请求头里，跟同源策略、Cookie 策略都无关。

  3. 多端复用接口时逻辑不统一
    App、小程序这类客户端没有浏览器 Cookie 机制，只能自己保存凭证，最后还是要走 Token。与其维护两套登录态，不如统一成无状态。

  4. 服务端要维护额外的状态
    每个在线用户都占一份 Session 内存，还要处理超时、并发会话控制等；而且只要凭证是靠 Cookie 自动携带的，就存在被 CSRF 利用的风险（这也是前后端分离常常直接 csrf().disable() 的原因）。

  5. 与接口的语义不匹配
    接口本身不记录”上次请求做了什么”，Session 在这里只是纯粹的额外状态。

如何禁用

SessionCreationPolicy 的几个取值：

取值 含义
ALWAYS 每次请求都创建 Session
IF_REQUIRED（默认） 需要时才创建，认证成功后一般会创建
NEVER 不主动创建，但如果别的地方创建了仍然会使用
STATELESS 完全不创建、也不使用 HttpSession

注意 NEVER 和 STATELESS 的区别：NEVER 只是”不主动创建”，一旦有别的代码调用了 request.getSession()，Session 依旧会存在、也依旧会被使用；而 STATELESS 是彻底不碰 Session。

禁用后的变化

配置为 STATELESS 后，SessionManagementConfigurer 在初始化时会把两个 SecurityContextRepository 都换掉（前提是没有显式调用过 http.securityContextRepository(...) 指定仓库，源码中会先判断共享对象是否为 null）：

  • 共享的 SecurityContextRepository 换成 RequestAttributeSecurityContextRepository，SecurityContext 只存在当前请求的 request attribute 里
  • SessionManagementConfigurer 自身使用的仓库换成 NullSecurityContextRepository（既不读也不写）

所以最终效果是：

  • Spring Security 不再创建 HttpSession，响应头里也不会再有 Set-Cookie: JSESSIONID（注意：业务代码若自己调用 request.getSession()，Servlet 容器依旧会创建 Session）
  • SecurityContext 只活在当前这一次请求里，请求处理完就没了（同一次请求内，SecurityContextHolder 依然能正常拿到认证信息）
  • RequestCache 被替换为 NullRequestCache，不会再”把被拦截的请求暂存起来，等登录成功后再跳回去”（这个功能本身就依赖 Session）
  • SecurityContextHolderFilter 仍然在过滤器链上，负责加载和清理上下文，只是它已经加载不到任何东西

登录认证成功之后，因为服务端不保存任何状态，这次认证信息在请求结束时就被丢弃了。此时再向其他接口发送请求，就相当于一个全新的匿名请求：Spring Security 不认识我们了，需要重新认证。

具体表现取决于有没有配置 formLogin()：

  • 没有配置 formLogin() 时，默认的 AuthenticationEntryPoint 是 Http403ForbiddenEntryPoint，会直接返回 403，响应体为空
  • 配置了 formLogin() 时，默认的 AuthenticationEntryPoint 是 LoginUrlAuthenticationEntryPoint，会先返回 302，Location 指向默认登录页 /login

（如果实际看到的是 403，说明当时还没有配置 formLogin()。）

本项目在上一章末尾已经配置了 formLogin(loginProcessingUrl("/auth/login"))，属于后一种：未认证的请求会先被重定向到默认登录页。又因为是前后端分离场景，前端不会把它当作页面跳转来处理，最终拿到的其实是这个登录页的 HTML 字符串。

注意事项

  • STATELESS 约束的是 Spring Security 对 Session 的读写，并不禁止业务代码自己调用 request.getSession()。但如果还继续用 Session 存数据，等于又把状态带了回来，而且在跨域场景下前端未必会带上 JSESSIONID。比如本项目的验证码就是存进 Session 的，这里更适合改成 Redis 之类的集中存储，或者干脆换成无状态的验证码方案。
  • 无状态与 CSRF 天然不太合得来：HttpSessionCsrfTokenRepository 在保存 token 时会调用 request.getSession()，从而又把 Session 建了回来，所以无状态方案下通常保持 csrf().disable()（本项目上一章已经关闭）。
  • 同理，rememberMe() 依赖持久化令牌和会话，在 STATELESS 下没有意义，不建议再配置。
  • logout() 也不再有 Session 可销毁，它只是清理本次请求的上下文，真正的”退出登录”要靠前端丢弃 Token（如果服务端需要让 Token 立即失效，还得配合黑名单 / 版本号等手段）。
  • 禁用 Session 只是不再”保存”登录状态，认证过程本身不受影响，登录接口依然会正常认证。
  • 真正让登录状态延续下去的是前端携带的凭证（Token）。所以启用 STATELESS 之后要配合 Token 方案，否则下一次请求就又是匿名用户了。
  • 可以在浏览器里观察：登录成功后响应头不再出现 Set-Cookie: JSESSIONID，就说明 Session 已经不再被使用了。
