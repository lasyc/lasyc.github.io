JWT

JSON Web Token (JWT) 是一种开放标准（RFC 7519），用于在不同方之间以 JSON 对象的形式安全地传递信息。JWT 是目前最流行的跨域认证解决方案，广泛用于用户认证和信息交换。

JWT 的结构

在线生成/解析

JWT 是一个由三部分组成的字符串，使用点 (.) 分隔：

  1. Header（头部）：包含元数据，如签名算法（如 HS256）。
  2. Payload（负载）：存储实际传递的数据，例如用户信息或声明（claims）。JWT 提供了 7 个官方字段，如 iss（签发者）、exp（过期时间）、iat（签发时间）等。
  3. Signature（签名）：把 Base64Url 编码后的 Header、Payload 用密钥做一次签名计算得到（HMAC 或非对称算法），用于验证数据有没有被篡改。

完整的 JWT 格式为：Header.Payload.Signature

JWT 的工作原理

服务器在用户认证通过后生成一个 JWT，包含用户信息和签名。客户端将 JWT 存储在 Cookie 或 localStorage 中，并在每次请求时将其附加到 HTTP 请求头的 Authorization 字段中：

Authorization: Bearer <token>

服务器通过验证签名来确认 JWT 的真实性，从而识别用户身份。

使用场景与特点

JWT 常用于无状态的分布式系统中，解决跨域认证问题。它的特点包括：

  1. 无状态：服务器无需存储会话数据，扩展性强。
  2. 安全性：通过签名防止数据篡改，但默认不加密，敏感信息需谨慎存储。
  3. 高效性：减少服务器查询数据库的次数。

注意事项

  1. 有效期设置：JWT 的有效期应尽量短，以减少被盗用的风险。
  2. 传输安全：必须通过 HTTPS 传输，避免明文泄露。
  3. 无法撤销：JWT 一旦签发，除非过期或额外逻辑处理，否则无法撤销。

合理使用 JWT，可以在不依赖服务端会话的前提下实现高效、安全的用户认证和信息传递。

生成 JWT

JWT 的字段分三个位置设置：Header、Payload、Signature（签名段不是字段，而是算出来的）。下面按位置梳理。

Header

字段 全称 用途
alg Algorithm 签名算法，如 HS256、RS256、ES256；none 表示不签名（危险，必须禁用/白名单校验）
typ Type 令牌类型，惯例填 JWT（很多库不校验，但建议带上）
kid Key ID 密钥标识。多密钥/轮换密钥时用它告诉服务端用哪把 key 验签
cty Content Type 当 Payload 又是嵌套 JWT 时填 JWT，一般不用
jku / jwk JWK Set URL / JWK 公钥来源，生产环境慎用（攻击者可伪造 URL 指向自己的公钥）
x5u/x5c/x5t X.509 系列 用证书链替代裸公钥
crit Critical 声明「以下扩展头必须被理解，否则拒绝」，用于强制校验

Payload

Payload 里官方（RFC 7519）定义了 7 个标准声明，其余都是自定义的：

字段 全称 类型 用途
iss Issuer String 签发者。服务端校验「这 token 是不是我（或可信方）签的」
sub Subject String 面向的主体，通常放 userId / username
aud Audience String/数组 接收方。校验「这 token 是不是发给我的」，防止 A 服务的 token 拿去调 B 服务
exp Expiration Time NumericDate 过期时间。校验时必查；单位是秒（不是毫秒）
nbf Not Before NumericDate 生效时间，早于此时间不接受
iat Issued At NumericDate 签发时间。可用于判断「密码修改后签发的 token 才有效」
jti JWT ID String 唯一 ID。配合 Redis 做黑名单/撤销、防重放（JWT 本身无法撤销，靠它补）

注意：exp / nbf / iat 在 JWT 里是秒级时间戳。用库的 Date / Instant 方法传值时库会自动换算，但手动拼 JSON 时容易错写成毫秒。
