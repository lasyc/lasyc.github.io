Spring Security 整合 JWT（一）

发表于2026-09-15|更新于2026-09-16|后端框架Spring Security
|总字数:5k|阅读时长:19分钟|浏览量:

项目搭建

前面已经讲完了「为什么要禁用 Session」和「JWT 是什么」，这一节把它们真正接到项目里。整体分四步：

  1. 先搭出一个基于 Session 的登录（Controller + Service 手动认证），确认功能可用；
  2. 禁用 Session，看看接口为什么会访问不了；
  3. 引入 JWT 和 Redis，让登录接口返回 Token；
  4. 加一个过滤器，每次请求从请求头取出 Token 完成认证。

登录接口（Session 版）

因为没有配置 formLogin()，登录请求不会经过 UsernamePasswordAuthenticationFilter，所以需要自己写一个登录接口，在 Service 中手动调用 AuthenticationManager 完成认证；UserDetailsService 则继续负责根据用户名提供用户信息，这一部分和之前是一样的。

这一节先保留 Session 方案把功能跑通，下一节再换成无状态。

AuthController

注意：AuthServiceImpl 中是通过 request.getParameter() 取值的（这也是 UsernamePasswordAuthenticationFilter 的做法），所以登录请求体要使用 application/x-www-form-urlencoded。如果想用 JSON 请求体，可以改成 @RequestBody 接收实体或 Map，再把取到的用户名、密码传给 Service。

AuthServiceImpl

AuthServiceImpl 同时实现了 AuthService（对外提供登录方法）和 UserDetailsService（按用户名查用户），是这一节的核心。

说明：HttpSecurity 的共享对象里默认并不包含 SecurityContextRepository（默认那套仓库是 SessionManagementConfigurer 在内部自己构建的），所以这个 Bean 不会被过滤器链自动采用。它之所以能生效，是因为 HttpSessionSecurityContextRepository 读写的是同一个 Session 属性键（SPRING_SECURITY_CONTEXT），过滤器链里的仓库同样能读到。这里把它定义成 Bean，主要是为了让 Service 中能注入并调用 saveContext()。

至此，基本的登录功能实现了，并且可以正常访问学生接口的增删改查。

禁用 Session

Session 版登录跑通之后，就可以迈出前后端分离的第一步了：不再让服务端保存登录状态，认证只在当前这一次请求内有效。

禁用 Session 之后，即使刚刚登录成功，再去访问学生接口的增删改查也会被拦截。这是符合预期的：登录时通过 securityContextRepository.saveContext() 写进 Session 的认证信息不会再被后续请求读取，之后每一次请求对 Spring Security 来说都是「未认证」的匿名请求。

想恢复访问，就得让每次请求自己带上凭证，也就是 Token。

引入 JWT

登录成功后由服务端签发一个 Token 返回给前端，之后前端每次请求都把它放进请求头：

服务端取出 Token、验签、解析出用户，再决定放不放行。Token 的生成与解析由上一章的 JwtUtil 负责。

引入 JJWT 依赖

JwtUtil

参照上一章节

JwtUtil 提供生成、解析、校验 Token 的能力，其中的 resolveToken() 用来从 Authorization 头中把裸 token 截取出来，下一节的过滤器会用到；密钥、有效期这些配置按上一章的 jwt.* 写好即可。

引入 Redis

Token 里虽然也能塞用户信息，但塞进去就改不了了：权限被调整、账号被禁用时，旧 Token 在过期前依然有效。所以这里的做法是「Token 只负责证明身份，用户信息另存一份」，用 Redis 保存用户对象。

这样还附带一个好处：服务端想强制某个用户下线，只要删掉 Redis 里的记录，他手里的 Token 就立刻失效了。

存储类型怎么选

Redis 的 value 有 String、Hash、List、Set、ZSet 等多种类型，理论上都能把用户对象「塞」进去，但语义差别很大。判断依据主要是访问模式：是整体读写，还是只关心其中几个字段。

String（当前做法）

  • 优点
    • 简单：一个 key 对应一个对象，序列化 / 反序列化由 Jackson 一次性完成
    • 一次网络往返就能拿到完整用户，正好匹配「认证时要把整个 User 取出来」的访问模式
    • 支持整体 TTL（set(key, user, Duration)），也能用 SETNX、INCR 做分布式锁、限流
  • 缺点
    • 想改一个字段，必须「整体读出来 → 改 → 整体写回」，并发下容易互相覆盖
    • 无法给单个字段设置过期时间

Hash

  • 优点
    • 字段级读写（HSET / HGET / HINCRBY），改权限、加字段不用动整个对象，冲突更小
    • 字段不多时用的是紧凑编码（listpack），内存通常比同样内容的 JSON 字符串更省
  • 缺点
    • 只有整体 TTL，不能给字段单独设过期（Redis 7.4 起才提供 HEXPIRE 等字段级命令）
    • 只能存扁平结构，遇到嵌套对象要么自己打平、要么把某个字段再塞一段 JSON
    • 取出后要手动把 Map 转成对象，写起来比整体反序列化啰嗦一些

其他类型

类型 直接拿来存用户对象 真正合适的用法
List RPUSH 之后要 LRANGE 0 0 才取得到，也没法按字段更新 登录历史、多端登录记录
Set 只有一个成员时，去重和集合运算都体现不出来 权限集合（SADD + SISMEMBER 判断有没有某个权限）
ZSet 只存一个对象，score 没有意义 在线用户列表（score 存最后活跃时间，便于按时间清理）
BitMap 只能存比特位 签到、活跃统计
HyperLogLog 只能存基数估计 UV 去重统计
Stream / Geo 与登录态无关 消息队列、地理位置

也就是说：承载「一个用户对象」用 String 或 Hash，其余类型更适合周边的集合类、统计类需求。

结论

这里的需求是「登录时整体写、每次请求整体读」，字段级读写完全用不上，所以 String + JSON 是最省事的选择，维持现状即可。什么时候需要考虑换或扩展：

  • 只想存 Token 本身、不存用户信息 → String 存一个字符串就够
  • 想存 Token、用户名、权限、登录时间等一组信息，且经常只改其中某一项 → Hash 更合适
  • 权限很多、只关心「有没有某个权限」→ 权限单独用 Set 存
  • 需要按「最后活跃时间」清理在线用户 → 用 ZSet

小提醒：如果之后把查询出来的权限一起放进 User 缓存，注意 SimpleGrantedAuthority 没有无参构造方法，Jackson 反序列化可能失败。更稳妥的做法是缓存一个自定义 DTO，权限用 List<String> 表示，需要时再转成 GrantedAuthority。

改造登录接口

登录本身的流程没变（还是把用户名、密码交给 AuthenticationManager 认证），变的只是认证成功之后做的事：

  • 原来：把 SecurityContext 保存进 Session；
  • 现在：把认证后的 User 存进 Redis，并签发一个 Token 返回给前端。

注意：这里 Redis 的过期时间写死为 24 小时，而 Token 的有效期来自 jwt.expiration-ms（上一章配置的默认值是 2 小时），两者并没有关联。Token 过期后即使 Redis 里还有用户信息也无法通过认证；反过来 Redis 先过期，Token 虽然还在有效期内，但取不到用户信息一样认证不了。实际项目中建议让两者的取值保持对应。

JWT 认证过滤器

从现在开始，前端每次请求都会带上 Token。我们要做的是：在 Spring Security 做鉴权（authorizeHttpRequests 里的那些规则）之前，从请求头取出 Token、查出用户，并把认证信息放进当前请求的 SecurityContextHolder。只有放进去，后面的授权规则才能看到 Authentication，进而决定放不放行。

JwtAuthenticationFilter 继承 OncePerRequestFilter，保证一次请求只执行一次。整体逻辑是「取 Token → 解析 → 查 Redis → 放认证信息 → 放行」，任何一步失败都不抛异常，直接放行交给后面的 Security 过滤器去拦截（最终返回 401 / 403）。

过滤器必须在鉴权之前执行，所以用 addFilterBefore() 把它挂在 UsernamePasswordAuthenticationFilter 之前（这里没有配置 formLogin()，过滤器链里其实并没有 UsernamePasswordAuthenticationFilter，它在这里只是作为一个排序位置来使用）

至此，登录后就可以继续访问学生接口的增删改查了。

注意事项

过滤器的注册方式

  • JwtAuthenticationFilter 没有标 @Component，而是在配置类里手动 new 出来、再用 addFilterBefore() 加入 Security 过滤器链。如果给它加上 @Component，Spring Boot 会把它当成普通 Servlet 过滤器再注册一次（注册在 Security 过滤器链之外）；由于 OncePerRequestFilter 内部有「已执行」标记，同一次请求并不会被处理两遍，但更规范的做法是用 FilterRegistrationBean 关掉自动注册。
  • 手动 new 意味着过滤器里的依赖（JwtUtil、RedisTemplate）要来自方法参数或自己的字段，不能靠 @Autowired 注入，写其他过滤器时同样要注意。

关于权限数据（authorities）

  • 过滤器里的 authorities 来自 Redis 中缓存的 User，而 loadUserByUsername() 里还留着一个 TODO，实际存进去的是空集合。等后面做权限校验时，需要把用户权限一起查出来并放进缓存，否则 hasAuthority(...) 之类的规则会全部失败。
  • 每次认证都是拿 Redis 里的授权信息，所以权限被修改后必须同步更新缓存，否则用户会一直拿着旧权限。小型系统如果不在意这些，也可以不用 Redis，每次认证回查一次数据库，直接拿最新权限。

关于登录态失效

  • 无状态之后 logout 没有 Session 可销毁：Token 在有效期内一直可用。想让它立即失效，得搭配 Redis 黑名单（用 JWT 的 jti）、用户版本号等手段，这也正是「JWT + Redis」组合的常见理由之一。

关于 Redis 存用户信息的取舍

  • 把用户信息存进 Redis，相当于服务端又保存了一份状态，只是不再依赖 Session、可以跨实例共享。这在实践中是很常见的折中：JWT 负责证明「这张票据确实是我签发的、且没有过期」，Redis 负责判断「这个用户现在还算不算数」，两者配合才能实现「登录态可以主动失效」。
  • 存 Redis 时用用户名作为 key，要求用户名唯一，而且用户改名时要额外处理，所以这里更推荐用 ID 作 key。

传统 Session在前面使用 Thymeleaf 的场景下，我们每次登录后台服务都会创建一个 Session，并且在响应时通过 Set-Cookie 把 JSESSIONID 写进浏览器的 Cookie；之后的每次请求都会自动携带这个 JSESSIONID，服务端据此就能知道用户的登录状态为已认证，从而允许其访问受保护的资源。 但是在前后端分离场景下，Session 虽然还能继续使用，却比较鸡肋：前端与后端通常不同源，想在跨域下携带 Cookie 要额外做不少配置（后端 config.setAllowCredentials(true) 只是其中一环），而且浏览器对跨站 Cookie 的限制也越来越严；后端多实例部署时，登录请求落在 A 服务器、后续请求落到 B 服务器，B 并不认识 A 发出的 JSESSIONID，就会判定用户未认证；此外像微信小程序、APP 这类客户端本身并没有浏览器 Cookie 机制。这几点会在下一节展开。 因此，在前后端分离的场景下，更推荐禁用 Session，不再在服务端保存用户状态：用户登录认证通过后，服务端根据用户信息生成一个唯一的令牌 Toke...
