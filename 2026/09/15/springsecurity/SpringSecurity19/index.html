自定义 UserDetailsService

因为没有配置 formLogin()，登录请求不会经过 UsernamePasswordAuthenticationFilter，所以需要自己写一个登录接口，在 Service 中手动调用 AuthenticationManager 完成认证；UserDetailsService 则继续负责根据用户名提供用户信息，这一部分和之前是一样的。

说明：HttpSecurity 的共享对象里默认并不包含 SecurityContextRepository（默认那套仓库是 SessionManagementConfigurer 在内部自己构建的），所以这个 Bean 不会被过滤器链自动采用。它之所以能生效，是因为 HttpSessionSecurityContextRepository 读写的是同一个 Session 属性键（SPRING_SECURITY_CONTEXT），过滤器链里的仓库同样能读到。这里把它定义成 Bean，主要是为了让 Service 中能注入并调用 saveContext()。

认证

从现在开始，后续的每一次请求都会携带 Token。我们要做的就是：在 Security 进行鉴权之前，从请求头中取出 Token 并完成认证，往 SecurityContextHolder 中放入认证信息。

并且需要将该过滤器添加到 UsernamePasswordAuthenticationFilter 之前（这里没有配置 formLogin()，过滤器链里其实并没有 UsernamePasswordAuthenticationFilter，它在这里只是作为一个排序位置来使用）

至此，登录后就可以继续访问学生接口的增删改查了。

注意事项

  • JwtAuthenticationFilter 没有标 @Component，而是在配置类里手动 new 出来、再用 addFilterBefore 加入 Security 过滤器链。如果给它加上 @Component，Spring Boot 还会把它当成普通 Servlet 过滤器再注册一次（注册在 Security 过滤器链之外）；由于 OncePerRequestFilter 内部有”已执行”标记，同一次请求并不会被处理两遍，但更规范的做法是用 FilterRegistrationBean 关掉自动注册
  • 过滤器里的 authorities 来自 Redis 中缓存的 User，而 loadUserByUsername() 里还留着一个 TODO，实际存进去的是空集合。等后面做权限校验时，需要把用户权限一起查出来并放进缓存，否则 hasAuthority(...) 之类的规则会全部失败
  • 无状态之后，logout 没有 Session 可销毁：Token 在有效期内一直可用。如果要让它立即失效，得搭配 Redis 黑名单（可以用 JWT 的 jti）或用户版本号等手段
  • 把用户信息存进 Redis，相当于服务端又保存了一份状态，只是不再依赖 Session、可以跨实例共享。这在实践中是很常见的折中：JWT 负责证明”这张票据确实是我签发的、且没有过期”，Redis 负责判断”这个用户现在还算不算数”，两者配合才能实现”登录态可以主动失效”
