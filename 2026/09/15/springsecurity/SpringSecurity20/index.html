Spring Security 整合 JWT（二）

发表于2026-09-15|更新于2026-09-17|后端框架Spring Security
|总字数:1.5k|阅读时长:5分钟|浏览量:

换一种写法：formLogin

上一节的登录是「自己写 Controller + Service，在 Service 里手动调用 AuthenticationManager」。这种方式灵活，能接收 JSON 请求体，代价是要自己维护 Controller 和 Service 两层。

这一节换用 Spring Security 自带的表单登录 formLogin：认证过程交给框架的 UsernamePasswordAuthenticationFilter 完成，我们只负责「认证成功之后做什么」和「认证失败之后返回什么」。

代价是无法再使用 JSON 请求体，原因见下面。

先把 Service 简化掉

改用 formLogin 之后，登录不再走 Controller，AuthServiceImpl 里的 login() 方法也就没用了，AuthenticationConfiguration 依赖同样可以去掉——这个类只剩下 UserDetailsService 的职责：

下面的代码仍然写着 implements AuthService，所以 AuthService 接口里的 login() 声明也要一并删掉，否则 AuthServiceImpl 会因为没有实现该方法而编译不通过；如果接口已经没有别的地方在用，也可以直接把 AuthService 整个去掉。

为什么不能用 JSON 请求体

UsernamePasswordAuthenticationFilter 内部是通过 request.getParameter("username") / request.getParameter("password") 取值的，它只认 application/x-www-form-urlencoded（以及 query string），请求体里的 JSON 它读不到。所以前端必须用表单格式提交，或者干脆改成上一节那种手动认证接口。

认证成功 / 认证失败的处理器

formLogin 默认的行为是「重定向」：成功跳首页，失败跳 /login?error。前后端分离下前端拿到的会是 302，必须用 Handler 换成 JSON 响应。

认证成功：CustomAuthenticationSuccessHandler

认证成功后要做的事，和上一节登录 Service 里做的事是一样的：把用户存进 Redis + 签发 Token；区别只是用户信息从 Authentication 参数里取，而不是自己调 AuthenticationManager。

这里的「存 Redis + 签 Token」和上一节 AuthServiceImpl#login() 做的事完全一样，只是取值来源换成了 onAuthenticationSuccess() 的参数。两处逻辑重复，实际项目里可以抽成一个公共方法（比如 TokenService#issue(User)）供两边调用，避免改了一处忘了另一处。

Redis 的 24 小时同样是写死的，和 jwt.expiration-ms 没有关联，注意点和上一节相同。

JSON 按项目已有的 JSON 库来选（例如 FastJSON2 的 com.alibaba.fastjson2.JSON），保持和 Result 的序列化方式一致即可。

认证失败：CustomAuthenticationFailureHandler

exception.getMessage() 会把具体原因（用户名或密码错误、账号被锁定等）直接返回给前端，调试时方便；生产环境建议换成固定文案，避免泄露框架内部信息。

配置过滤器链

最后把 formLogin 加进过滤器链：

几点说明：

  • loginProcessingUrl("/auth/login") 指定要拦截的登录地址，不需要再写对应的 Controller：请求会在过滤器链这一层就被处理掉，根本到不了 Controller。
  • successHandler / failureHandler 是可选的，不写就沿用默认的重定向行为。
  • 这里没有再写 .requestMatchers(HttpMethod.POST, "/auth/login").permitAll()：登录请求在 UsernamePasswordAuthenticationFilter 内部就被处理并直接返回响应，走不到授权环节，所以不需要为它开放白名单。白名单留给注册、验证码这类自己写的匿名接口即可。
  • http.formLogin() 会顺带把 UsernamePasswordAuthenticationFilter 注册进过滤器链，所以本节 addFilterBefore(..., UsernamePasswordAuthenticationFilter.class) 不再是「只借个位置」，而是真的挂在它前面。
  • 后续请求的认证依旧靠 JwtAuthenticationFilter，两者互不影响：一个负责「用账号密码换 Token」，一个负责「用 Token 换认证」。

两种方式怎么选

手动认证（上一节） formLogin（本节）
请求体 支持 JSON 只支持表单参数
需要的代码 Controller + Service 两个 Handler
认证过程 自己在 Service 里调 AuthenticationManager 框架的 UsernamePasswordAuthenticationFilter
成功后的处理 写在 Service 里（存 Redis + 签 Token） 写在 AuthenticationSuccessHandler 里
灵活度 高，认证前后可以插入任意逻辑 低，要改只能替换过滤器

两种方式最终都会走到同一个 AuthenticationManager，所以 UserDetailsService、密码编码器、JwtAuthenticationFilter 这些都是共用的，可以随时在两者之间切换。实际项目里前后端分离 + JSON 的场景更常见，用上一节的手动认证更顺手；formLogin 更适合快速搭 Demo 或服务端渲染的项目。
