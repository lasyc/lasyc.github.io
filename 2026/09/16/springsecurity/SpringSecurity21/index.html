Spring Security JWT 退出登录与 Token 失效

发表于2026-09-16|更新于2026-09-17|后端框架Spring Security
|总字数:3.8k|阅读时长:13分钟|浏览量:

写在前面

前两篇把「登录换 Token → 携带 Token 访问」这条链路跑通了，这一篇补上它的后半段：怎么让一个已经签发的 Token 失效。

JWT 本身无法撤销，只要签名正确、exp 没到就一直有效，所以「失效」只能靠服务端额外记一笔。整篇分三部分：

  1. 服务重启后让旧 Token 失效（用监听器清空 Redis）
  2. 主动退出登录
  3. Token 白名单与黑名单

让服务重启后 Token 失效

问题的由来

基于 Session 的实现里，登录态存在服务端内存中。服务一重启，内存里的 Session 就没了，前端拿着旧的 JSESSIONID 再来访问时，服务端查不到对应的 Session，只能判定「未认证」，要求重新登录。

换成 JWT + Redis 之后，这套「自动失效」的机制就没了：

  • Token 由服务端签发后交给前端保存，服务端不记录「我到底发给过谁」
  • Redis 里存的只是用户信息（username → User），它的作用是在每次请求时重新组装认证信息
  • 只要签名密钥没换、exp 没到，重启服务对这个 Token 没有任何影响

也就是说：重启后旧 Token 依然好用，这和 Session 时代的行为不一致。这里用 Servlet 的监听器，在服务启动时把 Redis 清掉，让行为重新对齐。

坑：authentication 永远是 null

上面这段代码跑起来，日志永远只会打印 authentication is null，后面删除 Redis 的逻辑一次也走不到。

原因不是「登出成功所以认证信息被清掉了」，而是**这次登出请求压根没经过 JwtAuthenticationFilter**：

  • 过滤器链里的顺序是 LogoutFilter → JwtAuthenticationFilter → …
  • 而 JwtAuthenticationFilter 是用 addFilterBefore(..., UsernamePasswordAuthenticationFilter.class) 加进去的，位置排在 LogoutFilter 后面
  • 而 LogoutFilter 匹配到登出请求后，执行完 Handler 就 return 了，不会再把请求交给后续过滤器

所以这个过程是：JwtAuthenticationFilter 没机会解析 Token、没往 SecurityContext 里放认证信息，LogoutFilter 拿到的就是空的：

如果是基于 Session 的写法（认证信息由 SecurityContextHolderFilter 从 Session 里恢复），这里拿到的 authentication 是有值的，所以这个方法在有状态项目里很常见。不要把它当成「登出后必然为 null」的固定结论。

验证

  1. 登录拿到 Token，用它访问 /student，正常返回
  2. 带同一个 Token POST /auth/logout，返回「退出成功」
  3. 再用这个 Token 访问 /student，会被拦截（401 / 403）

第 3 步正好说明了当前实现的性质：Token 本身并没有失效（签名有效、exp 也没到），只是 Redis 里对应的用户信息被删了，过滤器取不到用户就不会放认证信息，后续授权规则自然拒绝。

Token 白名单与黑名单

现状：这套实现其实已经是「白名单」

回看一下现在的认证链路：

  • 登录成功 → 把 User 存进 Redis，key 是 username
  • 每次请求 → 解析 Token 拿到 username → 从 Redis 取 User → 取得到才放认证信息

也就是说：Token 有效还不够，Redis 里必须有对应记录才认。这本质上就是一份白名单，只不过粒度是「用户」，不是「Token」。好处是登出能立即生效（靠删 Redis 实现）；局限也很明显：

  • 一个账号的所有端共用一个 key，任意一端退出、其他端一起掉线
  • 没法只让某一个 Token 失效（比如「把我在另一台设备上的登录踢掉」）

如果需要更细的控制，可以往下面两个方向走。

白名单：Redis 里存「有效的 Token」

思路：登录时把签发的 Token（或它的 jti）也存一份，请求时既验 Token 本身，也验 Redis 里有没有它。

两种常见的 key 设计：

key value 特点
login:token:{jti} username 按 Token 存，同一账号多端登录就有多条记录，登出只删自己那一条
login:token:{username} jti（或整段 Token） 按用户存，天然实现「同一账号只能一处登录」：新登录覆盖旧记录，旧 Token 立刻失效

优点：登录态完全由服务端掌握，登出、踢人、限制并发登录都好做。

缺点：服务端保存了全量登录状态。Redis 数据一丢，所有用户全部掉线；而且这跟 JWT「无状态」的初衷是冲突的，本质上又回到了 Session 的思路，只是换了存储介质。

黑名单：Redis 里存「失效的 Token」

思路反过来：默认信任所有签名正确、未过期的 Token，只把「被主动作废的 Token」记下来。

jti 在这里派上用场（前面 JWT 章节的 Payload 表里提过）：每个 Token 签出来时都带一个 UUID 作为 jti，相当于 Token 的身份证，拿它做黑名单的 key 最合适。

TTL 一定要设成「这个 Token 的剩余有效期」。Token 一旦自然过期就没有使用价值了，黑名单记录也该跟着消失；TTL 设短一点没影响，但忘了设就麻烦了——这些记录会永远留在 Redis 里越积越多。

优点：只为「被作废的 Token」占空间，正常 Token 不额外存储；Redis 出问题时最坏的结果是「已登出的 Token 又能用了」，不会让所有人掉线。

缺点：只能撤销已知的、还没过期的 Token；限制并发登录这类需求它做不了。

两者对比

白名单 黑名单
存什么 有效的 Token / jti 失效的 Token / jti
Redis 占用 与在线用户数成正比 只与被作废的 Token 数有关
Redis 丢数据 全部用户掉线 已登出的 Token 恢复可用
限制多端登录 可以（key 用 username，后登录覆盖先登录） 不能
立即登出 可以 可以
与无状态的契合度 低（保存全量状态） 高（只记例外）

选择上的经验是：

  • 只是想让登出立即生效 → 黑名单，开销最小
  • 还需要「单点登录」「限制同时在线设备数」→ 白名单
  • 两者可以叠加：白名单管「谁能登」，黑名单管「谁被踢」

注意：不要拿「Redis 里存 User」这套当黑名单。本文目前的实现属于「按用户的白名单」，删掉 User 等于把该用户所有 Token 一起作废。要精确到 Token，必须额外记录 Token 维度的信息（jti）。

顺带一提：版本号方案

如果需求是「一次让某个用户的所有 Token 全部失效」（比如改密码后强制所有设备重新登录），还有一种更省事的思路：

  1. 在用户表加一个字段（比如 token_version），或者放在 Redis 里
  2. 签发 Token 时把版本号写进 claims
  3. 校验时比对 Token 里的版本号和当前版本号，不一致就拒绝
  4. 改密码、强制下线时，把版本号 +1

它不用维护会持续增长的黑名单，代价是每次请求要多取一次版本号——如果版本号就存在 Redis 的 User 里，其实和现有的「取用户信息」是同一次查询，成本可以忽略。

注意事项

  • logout 默认地址是 /logout、方法只接受 POST；改成 /auth/logout 后前端记得用 POST 请求，logoutUrl 会被自动放行，不用再写 permitAll()
  • 登出成功后，前端也要清掉本地保存的 Token（localStorage）并重置页面状态；否则用户返回时旧 Token 还在请求头里，看起来就像「退出没生效」
  • 现在登出删的是 username 对应的记录，一个账号的所有端会一起下线；要支持多端独立，得换成 Token 粒度（见白名单 / 黑名单）
  • 用 ServletContextListener 清空 Redis 属于教学演示；生产环境里服务重启是常态（滚动发布、扩容），这么做会导致全量用户掉线，真要「重启即失效」优先考虑黑名单 / 版本号这类可控手段
  • 黑名单只需存字符串，用 Spring Boot 自动配置的 StringRedisTemplate 就够，不必为它再定义一个 RedisTemplate
  • 黑名单的 TTL 要按「Token 剩余有效期」计算，别忘设；否则 Redis 里会留下越来越多无用的 key
