Spring Security JWT + 权限校验

写在前面

到上一篇为止，认证链路已经完整了：登录拿 Token、请求带 Token，服务端据此识别出用户并放进 SecurityContext。但「知道你是谁」只是第一步，这一篇解决「你能做什么」。

上一章的 loadUserByUsername() 里还留着一个 TODO（权限集合给的是空集合），这里把它补上，然后给接口加权限要求，最后处理 401 / 403 的响应格式。

排查 403 的时候，就顺着这条链从下往上每段确认一遍。

把权限装进 UserDetails

上一章 loadUserByUsername() 里留着的 TODO 就是这里要补的内容：查询用户拥有的权限标识符和角色标识符，一起塞进 authorities。这一段和之前写的一样，参照即可。

建议保留之前的 .filter(StringUtils::hasLength)：selectPermissionCodeByUserId / selectRoleCodeByUserId 用的是 LEFT JOIN，用户没有角色或角色没有权限时会查出 null，直接 new SimpleGrantedAuthority(null) 会抛 IllegalArgumentException。

关于角色标识符：hasRole('ADMIN') 内部会自动补 ROLE_ 前缀，等价于 hasAuthority('ROLE_ADMIN')，而且区分大小写。所以数据库里 role.code 要存成 ROLE_XX 的形式（和第十章一致），否则 hasRole 永远不通过；如果库里存的是不带前缀的 ADMIN，那就要在注入 authorities 时自己补上 ROLE_，或者直接用 hasAuthority('ADMIN') 判断。

@EnableMethodSecurity 才会让 @PreAuthorize 生效（Spring Security 6 起默认就开启了 prePostEnabled，不用再写参数）。忘了加这个注解，@PreAuthorize 会被静默忽略，表现为「权限根本没生效」，是个很难一眼看出的坑。

同一套权限规则也可以写在 authorizeHttpRequests 里，比如 .requestMatchers(HttpMethod.DELETE, "/student").hasAuthority("student:delete")。区别是：注解离业务方法近、适合细粒度控制；集中配置能一眼看全所有规则，两者按习惯选即可。

踩坑：所有接口都返回 403

按上面配好之后登录测试，会发现访问学生接口的增删改查全部返回 403，连权限最全的账号也一样。

原因在 JwtAuthenticationFilter 里：构造认证信息时把权限集合传成了 null。

AbstractAuthenticationToken 对 null 的 authorities 会当作空集合处理（所以不会 NPE），于是结果是：身份认证通过了，但一个权限都没有，hasAuthority(...) 全部返回 false。

这里出现的是 403 而不是 401，正好说明了两者的区别：请求已经认证成功了（Token 有效、Redis 里也有用户），只是授权不通过，所以走的是 403。401 留给「认证就没过」的情况，下一节要处理的正是它。

顺带一个容易困惑的问题：刚改的 loadUserByUsername() 明明查了权限，为什么改过滤器之前还是 403？因为权限是在登录时随 User 一起写进 Redis 的，之前存的那份 authorities 还是空的。改完代码后要重新登录一次（或者先清掉那条 Redis 记录）才会写入新数据。

自定义 401、403 处理器

先分清 401 和 403

触发场景 由谁处理 默认行为
401 未认证 没带 Token、Token 过期/签名不对、Redis 里查不到用户 AuthenticationEntryPoint 取决于配置（见下）
403 无权限 已认证，但 hasAuthority / hasRole 不通过 AccessDeniedHandler AccessDeniedHandlerImpl，返回 403 但响应体为空

这两个组件都是在 ExceptionTranslationFilter 里被调用的：它包在授权过滤器外面，捕获后面抛出的 AuthenticationException / AccessDeniedException，再分别交给入口点和拒绝处理器。

（如果当前是匿名用户，即使原因是「权限不足」也会走入口点，因为对系统来说「你还没登录」。）

为什么返回的是 302 而不是 401

关键在于 AuthenticationEntryPoint 的默认实现是「看配置挑」的：

  • 配过 formLogin()（前面几章正在用）→ 默认入口点是 LoginUrlAuthenticationEntryPoint，它的行为是重定向到登录页，所以前端看到 302
  • 什么登录方式都没配 → 默认入口点是 Http403ForbiddenEntryPoint，返回的是 403（注意，不是 401）

也就是说，默认配置下根本不会返回 401，必须自己指定。JWT 方案里没有登录页可跳，前端要的是一句能判断的 JSON，所以把入口点换成返回 401 的实现正合适。

而 403 这一路本来就是 403，只是响应体是空的，前端拿不到提示信息，所以顺便也自定义一下。

未认证：CustomAuthenticationEntryPoint

无权限：CustomAccessDeniedHandler

注册到过滤器链

这两个处理器是全局的：JwtAuthenticationFilter 里遇到 Token 无效一律「放行交给后面的 Security 拦截」，最终返回的就是这里写的内容，所以过滤器本身不需要写任何响应逻辑。

小结

  • 权限数据要在 loadUserByUsername() 里查出来、放进 authorities，并且确保 JwtAuthenticationFilter 把它传进 Authentication——这两处缺一个，@PreAuthorize 就全部失败
  • 角色标识符区分大小写，且 hasRole('X') 匹配的是 ROLE_X
  • @EnableMethodSecurity 不能忘，否则注解被静默忽略
  • 401 和 403 要自己配 Handler 才有像样的 JSON 响应；配了 formLogin() 时默认入口点还会 302 重定向
  • 权限是登录时随 User 缓存进 Redis 的，改了权限查询逻辑后记得重新登录或用新数据覆盖缓存，否则读到的还是旧权限
