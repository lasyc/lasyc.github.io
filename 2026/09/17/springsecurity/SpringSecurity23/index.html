Spring Security JWT + 验证码

发表于2026-09-17|更新于2026-09-17|后端框架Spring Security
|总字数:2k|阅读时长:7分钟|浏览量:

背景：验证码不能再存 Session 了

之前生成验证码后是直接存进 Session 的（见《Spring Security Remember Me 与验证码》），服务端靠 JSESSIONID 把「这次生成的验证码」和「这个浏览器」对应起来。

现在 Session 已经禁用，服务端不记任何会话状态，于是验证码遇到一个最基础的问题：

服务端把验证码交给前端之后，下次请求带上来的验证码，怎么知道对应的是哪一次生成的结果？

Session 时代的答案是「同一个 JSESSIONID」，现在这个答案没了，那就自己造一个标识：生成验证码时顺便发一个 UUID，

  • Redis 里存 captcha:{uuid} → 验证码，带 5 分钟 TTL
  • uuid 返回给前端
  • 登录时前端把它带回来，服务端拿 uuid 查出验证码，再和请求里的 captcha 参数比对

也就是说：用「Redis 的 key」替代「Session」，状态放到集中存储里，而不是绑在某次会话上。这和 JWT 的思路是一致的：Token 证明「身份是我签发的」，而 uuid 只负责「把我这次的验证码找回来」。

几点说明：

  • 这里用 StringRedisTemplate：Key 和 Value 都是字符串，用它就不用再自定义 RedisTemplate，而且能直接和 Spring Boot 的自动配置对上
  • log.info 打印验证码只为开发调试，上线前要去掉
  • uuid 用 Cookie 交给前端是最省事的一种做法（浏览器会自动回传），但并不是无状态场景的常规选择，原因见最后的注意事项；换成「写在响应体或响应头里、由前端保存并在登录时一并提交」会更统一

校验验证码过滤器

验证码的校验时机很重要：必须在认证之前完成。因为验证码本质上是一道「防机器人」的门，如果先校验账号密码、后校验验证码，攻击者可以直接把密码错误与验证码错误的响应区分开来，验证码就形同虚设。

所以这里继续用自定义过滤器（和之前的 Session 版思路一样）。流程是：只拦登录请求 → 取请求参数里的 captcha → 从 Cookie 里取 uuid → 从 Redis 取对应验证码 → 比对。任何一步失败都直接写响应并 return，不再继续往下走，这样账号密码的校验就不会发生：

注意事项

关于用 Cookie 传 uuid

这里通过 Cookie 将唯一标识符传给前台，在无状态场景下并不推荐：Session 已经被禁用，Cookie 本质上也是「服务端靠它认人」的机制，用它相当于又把会话带了回来。更推荐的做法是：

  • 生成接口把 uuid 放在响应体里（如 Result.success().data("uuid", uuid)）或响应头里
  • 前端自己保存（内存 / localStorage），登录时连同 captcha 一起提交

两个细节要注意：

  • 如果前端与后端不同源，Cookie 还要配 SameSite / Secure，前端要开 withCredentials，后端 setAllowCredentials(true)——这也正是前面禁用 Session 时列举过的麻烦
  • 如果继续用 Cookie，至少补上 cookie.setPath("/")：不显式设置时，浏览器会按默认规则推导 path，一旦路径变了就很有可能带不回来

关于两个容易踩的点

  • request.getCookies() 在客户端一个 Cookie 都没带时会返回 null，所以上面的代码先判了空再 Arrays.stream(...)。用 Postman 之类不带 Cookie 的工具直接调 /auth/login 就能复现，不判空会直接 NPE（返回 500 而不是预期的 400）
  • 过滤器挂在 JwtAuthenticationFilter 之前（该类定义在《整合 JWT（一）》里，不是 CustomJwtAuthenticationFilter），名字写错的话 addFilterBefore 会直接编译不过

关于一次性与防刷

  • 验证码应该一次一用：校验通过后立即删除。当前代码已经做到了，但要注意顺序——先删除再 filterChain.doFilter()，否则并发请求可能重复使用同一个验证码
  • 带来的副作用是：密码输错时验证码也已经被消耗，前端必须重新获取一张；如果想让体验好一点，可以把删除动作挪到「认证成功之后」，代价是同一个验证码在这段时间内可以被重复使用
  • 只删「成功的」也不够：失败不限次数的话，攻击者可以固定一张验证码不断试密码。常见做法是同一 uuid 连续失败几次就作废（在 Redis 里用一个计数器），或者配合登录失败锁定
  • 只拦 /auth/login 是可行的，但如果项目有多个需要验证码的接口（注册、短信发送等），把地址写成可配置的列表会更灵活

到这里 JWT 方案的几块拼图就齐了：登录发 Token、过滤器认 Token、异常返回 401/403、权限校验、验证码防刷。用现在的实现回头再看一次，Server 端确实只在 Redis 里保留了一份用户信息，其余都靠 Token 自己携带——这也是无状态认证好扩展、却也难以「立即失效」的根源。
