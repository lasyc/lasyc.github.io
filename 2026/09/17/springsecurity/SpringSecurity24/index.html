前面二十多篇，不管是表单登录、Remember Me，还是自己签 JWT，本质都是「我们自己当认证中心」——账号密码存在自己的库里，登录状态由自己确认。

这一篇换个方向：把认证这件事交给别人。也就是「使用 Gitee / GitHub / 微信登录」这种场景，协议层面就是 OAuth 2.0。

内容按三层展开：

  1. 第三方授权到底解决什么问题（为什么不能把密码给别人）
  2. OAuth 2.0 的协议细节（重点是授权码模式）
  3. Spring Security 怎么把它集成进来，以及和前面 JWT 方案怎么衔接

第三方授权

从一个场景说起

假设我们做了个博客系统，想让用户能用 Gitee 账号直接登录，登录之后我们还想拿到他的 Gitee 昵称和头像显示在页面上。

最直觉的想法是：让用户把 Gitee 账号密码填给我们，我们拿他的账号密码去 Gitee 登录，再把信息抓回来。

这个方案有三个致命问题：

  • 用户凭什么信任我们？把 Gitee 密码交给一个第三方网站，风险和把银行卡密码写纸条上差不多
  • 一旦泄露，用户整个 Gitee 账号就没了，而且他很可能在别的地方用了同一个密码
  • 我们还得负责保管别人的密码，这本身就是一个巨大的安全责任

所以这个思路必须放弃。

正确的做法

换个思路：让用户自己去 Gitee 登录，Gitee 给他发一张「通行证」，他把通行证交给我们。

  • 用户在 Gitee 页面上输入密码 —— 密码只经过 Gitee，我们全程看不到
  • Gitee 问用户：这个网站想读你的昵称和头像，同意吗？（这就是「授权」）
  • 用户同意后，Gitee 发一张有时效、有范围的通行证
  • 用户把通行证转交给我们，我们拿它去 Gitee 换用户信息

这样我们的服务器从来没有接触过用户的密码，而且万一通行证泄露了，它也有有效期、有权限范围，损失可控。

可以类比成代客泊车：你把车钥匙交给泊车员（通行证），他能发动车、能在停车场里挪车，但开不走（权限范围受限），而且这张钥匙出了停车场就没用（有效期）。你不需要把自己的身份证、家门钥匙都给他。

四个角色

OAuth 2.0 里给这四方各起了个名字，后面看文档会经常遇到：

角色 英文 是谁 在「用 Gitee 登录博客」里
资源所有者 Resource Owner 数据的主人 用户本人
客户端 Client 想拿数据的一方 我们的博客系统
授权服务器 Authorization Server 发通行证的 Gitee 的授权端点
资源服务器 Resource Server 存数据的 Gitee 的用户信息接口

注意授权服务器和资源服务器通常是同一个平台的两个功能（Gitee 既是发证的也是存数据的），但在协议里是两个独立概念，可以拆开（比如你自己搭一个认证中心，业务服务只当资源服务器）。

它不是「登录协议」

有个概念特别容易混：OAuth 2.0 解决的是「授权」，不是「认证」。

  • 「授权」= 资源所有者同意客户端访问他的资源（这是 OAuth2 的 original 目标，比如让第三方应用读取你的相册）
  • 「认证」= 确认「现在操作的是谁」

所以严格来说，OAuth2 并没有规定「怎么告诉你这个用户是张三」。很多平台提供的「用 Gitee 登录」其实是在 OAuth2 之上又补了一层，那层叫 OIDC（OpenID Connect），它规定了一张 id_token，里面写着用户的身份信息。

区别在实践中很好判断：只拿到 access_token 和用户信息接口，那是纯 OAuth2；如果响应里还多了一个 id_token（一个 JWT），那就是 OIDC。

Spring Security 里 OidcUser 和 OAuth2User 的区分就来自这里。

OAuth 2.0

OAuth 2.0 是一个授权框架（RFC 6749），核心目标一句话：

让客户端在不拿到用户密码的前提下，获得访问用户在某个服务上受限资源的凭证。

它规定了四种拿凭证的方式（官方叫「授权许可类型」，Grant Type）：

模式 大致流程 适用场景 现状
授权码模式 先拿 code，再用 code 换 token 有服务端的 Web 应用、App 最主流、最安全，本篇重点
隐式模式 授权后直接把 token 放在 URL 里返回 纯前端单页应用 已废弃，OAuth 2.1 中移除
密码模式 用户直接把密码交给客户端，客户端拿去换 token 自己家的 App 连自己家的服务 已废弃，OAuth 2.1 中移除
客户端凭证模式 没有用户参与，客户端用自己的身份换 token 服务与服务之间调用 仍在使用

日常说的「第三方登录」，用的都是授权码模式。

授权码模式的完整流程

把关键几步拆开看：

  1. 发起授权请求：客户端拼一个 URL，把 client_id（我是谁）、scope（我要什么权限）、redirect_uri（回来找谁）、state（一个随机值）带上去，让浏览器跳过去。这一步不涉及任何机密信息，所以可以在前端做。
  2. 用户授权：在第三方的页面上完成登录和同意。这一步密码不经过客户端，这是整套机制的前提。
  3. 回调带 code：第三方把用户重定向回回调地址，URL 上带一个一次性的 code。
  4. 用 code 换 token：这一步是客户端服务器直接请求授权服务器（不是通过浏览器），并且要带上 client_secret。换回来的 access_token 就是那张通行证。
  5. 拿 access_token 取数据：请求资源服务器，通常放在请求头 Authorization: Bearer {access_token}。

为什么要多给一个 code

这是最容易困惑的设计：既然最后要的是 access_token，为什么第三步不直接把 token 给回来，非要绕一层 code？

原因是泄露风险不对等：

  • 第三步的重定向是经过浏览器的，URL 会出现在地址栏、浏览器历史、Referer、服务器日志里。如果直接把 token 放在这里，等于把它写在墙上
  • 而 code 换 token 这一步是客户端服务器发起的，要带上 client_secret（客户端和授权服务器之间的密码）。光有 code 拿不到 token

两个条件叠在一起：code 就算被看到了，攻击者也换不出 token；而 client_secret 从不出现在浏览器里。此外 code 还是一次性的、有效期很短（通常几十秒到几分钟），用完即废。

state 参数防的是什么

state 是客户端自己生成的随机字符串，在发起授权时带上，回调时校验是否和自己存的一致。

它防的是 CSRF：攻击者拿自己的账号走一遍授权流程，拿到一个合法的 code，然后构造一个链接 .../login/oauth2/code/gitee?code=攻击者的code 诱骗你点击。如果你的应用不校验 state，就会拿这个 code 去换 token，最后你的浏览器上登录的变成了攻击者的账号。之后你在上面做的操作（比如绑定的个人信息）就全记到攻击者账号下了。

有了 state，回调时发现这个值和自己存的对不上，流程直接中断。

OAuth 2.1 变了什么

OAuth 2.1 是把 OAuth 2.0 十几年的实践和修补整合成的一份新规范（目前仍是草案性质），主要变化：

  • 移除隐式模式和密码模式，只保留授权码模式和客户端凭证模式
  • 授权码模式强制要求 PKCE（防止授权码被拦截后重放，对公开客户端尤其重要）
  • 强制要求 redirect_uri 精确匹配
  • 明确 Bearer Token 的使用规范（不能放在 URL 里）

可以理解为：新项目只管用授权码模式（最好加上 PKCE）就对了，另外三种要么已废弃，要么场景很窄。

Spring Security 集成 OAuth2

Spring Security 把客户端的这套流程封装成了 OAuth2Login：只需要配置「我是谁（client-id/secret）、要去哪授权（provider）」，剩下的拼 URL、存 state、换 token、调用户信息接口，框架全包了。

引入依赖

这个 starter 会带进来 spring-security-oauth2-client（客户端流程）和 spring-security-oauth2-jose（处理 OIDC 的 JWT）。

client 和 resource-server 是两种角色

OAuth2 相关有三个 starter，容易看花眼，区别在于我们在这个流程里扮演哪一方：

starter 我们的身份 干什么 什么时候用
spring-boot-starter-oauth2-client 客户端 主动去第三方拿授权、换 token 第三方登录（本篇场景）
spring-boot-starter-oauth2-resource-server 资源服务器 被动接收别人带来的 token 并校验 别人拿 token 访问我们
spring-boot-starter-oauth2-authorization-server 授权服务器 自己发 token 自己搭认证中心

resource-server 是「校验别人签发的 token」用的，它负责：从 Authorization: Bearer xxx 里取出 token → 去授权服务器拉公钥（或按配置的密钥）验签 → 校验 iss、exp、scope，最后塞进 SecurityContext。

而这个项目里，token 从签发到校验都是自己做的：JwtUtil 用 JJWT 生成和解析，JwtAuthenticationFilter 从请求头取出来验一遍再放进 SecurityContext。也就是说，**JwtAuthenticationFilter 干的其实就是「资源服务器」那份活**，只不过是用 JJWT 手写的版本。既然没有「接受别人签发的 token」这个需求，自然用不上这个 starter。

什么情况下会需要它：

  • 项目拆成「认证中心 + 业务服务」两部分，业务服务只负责校验认证中心签的 JWT。这时自定义过滤器可以被 http.oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults())) 替代，验签交给 Nimbus（也就是第 18 章那张表里说的场景）
  • 服务之间互相调用，上游签发的 token 要在下游校验
  • 接口要接受第三方平台发的 access_token

反过来说，只要 token 是自己签、自己验，这个 starter 就不需要引入。

Spring Boot 4 里新增了一套按模块命名的 starter，对应的名字是 spring-boot-starter-security-oauth2-client，两个都能用。这里用传统的名字，和前面的 spring-boot-starter-security 保持一致。

底层发生了什么

加上 oauth2Login() 之后，过滤器链里多了两个过滤器：

过滤器 拦的地址 干什么
OAuth2AuthorizationRequestRedirectFilter /oauth2/authorization/{registrationId} 组装授权请求、生成 state、暂存请求，然后 302 到第三方
OAuth2LoginAuthenticationFilter /login/oauth2/code/{registrationId} 校验 state → 用 code 换 access_token → 调用户信息接口 → 构造 Authentication

这正好对应授权码模式的第 1、2 步和第 3~5 步，中间「用户在第三方登录授权」那一步是在别人的页面上完成的，我们管不着。

登录成功后，SecurityContext 里放的是一个 OAuth2AuthenticationToken，它的 principal 是 OAuth2User（如果是 OIDC，则是 OidcUser）。

回调地址的「接口实现」在哪

http://localhost:8080/login/oauth2/code/gitee 这个地址很容易让人以为要写个 Controller 去接它。实际上不用，也接不到。

它由 OAuth2LoginAuthenticationFilter 通过 filterProcessesUrl 拦截处理，位置在过滤器链上，比 DispatcherServlet 更早。请求走到这里就已经被处理完了，自己再写一个 @GetMapping("/login/oauth2/code/gitee") 是不会被调用的（真写了只会以为自己没生效）。

前面几篇的 JWT 方案里，登录成功后是「存 Redis + 签 Token」。第三方登录成功后可以用同样的思路处理，因为过滤器链上正好留了成功处理器的位置：

这样两套登录方式就能共用一个 Token 体系：账号密码登录和第三方登录只是拿身份的方式不同，拿到身份之后都走「签发 JWT」这一步。

注意事项

① 这套流程离不开 Session

前面为了 JWT 我们禁用了 Session，而 OAuth2 登录默认需要 Session：从「跳去 Gitee」到「回调回来」之间隔了用户操作，那个授权请求（含 state）必须有个地方暂存，Spring Security 默认用的就是 HttpSessionOAuth2AuthorizationRequestRepository。如果项目里配了 sessionManagement() 的无状态策略，这条链路会直接走不通。

常见处理办法：

  • 这一部分功能不参与无状态，让它正常使用 Session（最简单，多数项目就是这么做的）
  • 自定义 AuthorizationRequestRepository，把授权请求存到 Cookie 或 Redis 里（工作量稍大，但和无状态方案一致）

② 走一遍流程时可以用日志观察

把 org.springframework.security 的日志级别调到 DEBUG，就能看到 /oauth2/authorization/gitee、/login/oauth2/code/gitee 这两个地址的进出，以及换 token、调用户信息接口的过程，比盲猜快得多。

③ 回调地址必须和注册时填的一模一样

协议、域名、端口、路径任何一处不同都会被平台拒绝（这一步是授权服务器在判断，不是我们自己的代码）。本地开发时换端口、把 localhost 换成 127.0.0.1，都可能踩到（Gitee 回调地址一栏可以提前把几种写法都填上）。

④ 只有一个客户端时，行为会「自动」

oauth2Login() 里如果只注册了一个客户端，未登录访问受保护资源时会被直接 302 到第三方授权页；注册了多个客户端时，才会生成一个让你选平台的默认登录页（/login）。所以「为什么我没写跳转代码就跳到 Gitee 了」这个现象是正常的。

⑤ client-secret 不要提交到 git

它相当于客户端在授权服务器那边的密码。用环境变量或配置中心注入比较稳：

⑥ 前后端分离下「返回 JSON」这件事有点别扭

第三方登录的整条链路都是浏览器重定向，成功之后浏览器停在你的回调地址上。这时候如果成功处理器直接写一段 JSON，用户看到的就是一屏 json 文本。常见做法是让成功处理器再 302 回前端页面、把 token 放在 URL 参数里（或先换一个一次性 code 再让前端拿这个 code 换 token）。

这也说明第三方登录更适合「服务端渲染 / 单页应用直接整页跳转」的场景；如果前端是 SPA、调接口的全是 AJAX，那么更常见的形态是：前端自己开一个小窗口走第三方授权，拿到 code 后把 code 交给后端换取自己的登录态。

⑦ 非内置平台一定要写 authorization-grant-type

这一条单独拎出来说，因为它的表现是应用根本起不来，而不是登录时报错，第一次遇到容易往错误的方向查。凡是看到下面这个栈，直接去看 registration 里有没有 authorization-grant-type: authorization_code：

Github / Google / Facebook / X / Okta 这些内置平台不写也不会报，正因为如此，照着内置平台的示例去配 Gitee、微信、QQ 时特别容易漏掉。

小结

  • 第三方授权用一张「有时效、有范围」的通行证，换掉了「把密码交给别人」这个做法，核心收益是密码不外泄、权限可收窄、凭证可过期
  • OAuth 2.0 是授权框架不是登录协议，真正规定「你是谁」的是它上面的 OIDC（多一张 id_token）
  • 四种模式里新项目只需要关心授权码模式，其中两个关键角色是 code（一次性、给浏览器看的）和 client_secret（保密、只走服务端），state 用来防 CSRF
  • Spring Security 里接第三方登录，最少的改动就是「一个依赖 + 一段 registration / provider 配置 + 一句 oauth2Login()」；自定义 SecurityFilterChain 的项目必须自己写这一句
  • /login/oauth2/code/{registrationId} 这个地址是过滤器处理的，不用（也接不到）自己写 Controller；要定制行为就从 successHandler / failureHandler / OAuth2UserService 三个口子进去；想彻底自己控制，就绕过 oauth2Login() 写一个普通接口接 code
  • 想接进自己的用户体系，就自定义 OAuth2UserService（把第三方用户映射成本地用户）和成功处理器（签发自己的 Token）
  • 唯一的硬性限制是：OAuth2 登录流程默认依赖 Session，和彻底无状态的 JWT 方案本质上是要权衡一下的

到这里，这套笔记从「过滤器链是怎么走的」一路写到了 OAuth2。回头看整个脉络：认证（谁能登进来）→ 授权（能干什么）→ 会话（怎么记住他）→ 无状态（不用 Session 怎么办）→ 第三方认证（不自己记密码怎么办）。框架本身在变，要解决的问题一直没变。
