Spring AI 对话记忆

发表于2026-10-03|更新于2026-10-03|后端框架Spring AI
|总字数:2.6k|阅读时长:10分钟|浏览量:

对话记忆

大模型是无状态的，即不会保留之前的交互信息，每一次对话都是一次新的对话

因此，在实际开发时，我们需要自己维护对话记录，每次有新的对话时，需要连同历史对话一起发送给 AI 大模型，基于历史对话来对新的问题做出回答

参照之前的案例搭建一个简易的工程

访问 http://localhost:8080/chat?message=我叫lasyc，等待 AI 回复

此时再访问 http://localhost:8080/chat?message=我叫什么

ChatMemory

ChatMemory 是一个接口，是用于管理对话记忆的，它只有一个实现类就是 MessageWindowChatMemory，默认最大保存 20 条对话记录

这次访问时需要携带 conversationId 并且每次对话时值必须是一样的，因为 ChatMemory 中使用 conversationId 作为主键保存历史对话，新开对话的话只需要修改 conversationId 即可

访问 http://localhost:8080/chat?message=我叫lasyc&conversationId=123

访问 http://localhost:8080/chat?message=我叫什么&conversationId=123

如果使用了 SimpleLoggerAdvisor，通过 log 也可以看出来，第二次请求时将前一轮的用户信息和 AI 回复信息都再次发送给了 AI 大模型

查看源码可以发现，MessageWindowChatMemory 中，是基于 InMemoryChatMemoryRepository 实现的，默认将对话历史保存在内存中

MessageChatMemoryAdvisor

上述示例中，我们是自己手动维护对话记忆，还是比较麻烦的，在前边学习 Advisor 的时候，有一个名为 MessageChatMemoryAdvisor 的实现类，它就是专门用于维护对话记忆的

聊天记录最大上限

上面提到了 MessageWindowChatMemory 中默认最多存储 20 条对话记录，其中包括了用户信息和大模型回复信息，也就是一共 10 轮对话

如果使用了对话记忆功能，那么多次对话时，都会将历史对话一起发送给大模型，当多轮对话之后，历史对话也会变多，大模型可以接收的上下文长度也是有上限的，具体请查看大模型厂商的官方文档

因此设计一个合理的对话记录上限尤为重要

对话存储

上面提到了 ChatMemory 默认使用的 InMemoryChatMemoryRepository 来将对话记录存储到内存中，除此之外，还支持将对话记录存储到数据库中，如：JDBC、Redis 等

Redis 存储

上面的示例中使用了 JDBC 作为存储工具，但是每次发送请求时都要从数据库获取对话记录，对于大型项目来说，这点性能损耗还是需要避免的，因此我们可以使用 Redis，直接从内存中获取。

因为 RedisChatMemoryRepository 需要 Redis Stack / Redis 8，但是我用的是 windows 版本 redis，这里使用 Docker 启动 Redis Stack

访问 http://localhost:8080/chat?message=我叫lasyc&conversationId=123，再通过 Redis 客户端可以看到 Redis 中已经保存了历史对话记录

多层记忆架构

记忆越多，AI 就越聪明，给出的回答就越有效，但是随着记忆增多，会触发 Token 上限，因此，即使数据库中保存了 200 乃至更多的聊天记录，为了保证不触发 Token 上限，也只能选择最近的 100 条记录发送给 AI 大模型

多层记忆架构就是为了解决这个问题，将 AI 的对话记录，根据时间和存取方式分为：短期记忆、中期记忆、长期记忆

  1. 短期记忆：选取最近的 N 条记录作为短期记忆
  2. 中期记忆：通过 RAG 检索相关的历史对话作为中期记忆
  3. 长期记忆：关键信息的固化总结
    • 定期对对话记录进行总结提炼，提取关键信息
    • 在特定节点对对话记录进行总结提炼，提取关键信息
