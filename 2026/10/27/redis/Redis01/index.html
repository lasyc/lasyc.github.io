初识 Redis

认识 NoSQL

在前面我们学习了 MySQL，MySQL 属于关系型数据库，而 Redis 则属于非关系型数据库，我们称之为 NoSQL

对比维度 关系型数据库 非关系型数据库
数据结构 结构化（表、行、列） 非结构化或半结构化（键值、文档、图等）
数据关联 通过外键关联，支持 JOIN 一般不建关联，靠数据冗余和应用层维护
查询方式 SQL 各产品专属查询语句
事务特性 严格遵循 ACID 多数遵循 BASE，部分产品支持有限事务
存储方式 以磁盘为主 内存（Redis）、磁盘（MongoDB、HBase）等
扩展性 以垂直扩展为主 以水平扩展为主

认识 Redis

Redis 全称 Remote Dictionary Server，意为远程字典服务，是一个基于内存的键值对型 NoSQL 数据库

  1. 键值对型：value 支持多种不同的数据结构
  2. 单线程执行命令：每个命令具备原子性；Redis 6.0 起网络 I/O 改为多线程，但命令执行仍是单线程
  3. 低延迟、速度快：基于内存，I/O 多路复用，数据结构实现高效
  4. 支持数据持久化（RDB、AOF）
  5. 支持主从集群、分片集群

安装 Redis

Redis 官方只提供 Linux 和 macOS 版本，不维护 Windows 版本。Windows 上运行的是第三方编译的版本（如微软早年的 3.2 移植、社区维护的 redis-windows），版本通常落后于官方，部分新特性可能缺失

这里使用 Windows 版本

  1. 解压后打开 start.bat 启动 Redis 服务
  2. 再次打开 redis-cli.exe 连接 Redis，进入命令行操作窗口（默认地址 127.0.0.1，端口 6379）

简单使用：

  1. 保存值：SET key value
  2. 获取值：GET key

Redis 常见命令

Redis 是一个 key-value 数据库，key 一般是 String 类型，但 value 的类型多种多样

五种基本数据类型

类型 说明 典型用途
String（字符串） 最基本类型，可存字符串、整数、浮点数，单个最大 512MB 缓存对象、计数器（INCR）、分布式锁（SETNX）、Session
Hash（哈希） field-value 的无序字典，适合存对象 用户信息、商品详情、购物车（field 为商品 ID，value 为数量）
List（列表） 有序、可重复，支持两端插入和弹出 消息队列（LPUSH + BRPOP）、最新 N 条记录、时间线
Set（集合） 无序，元素不重复 去重、标签、共同好友（交集 SINTER）、抽奖
Sorted Set / ZSet（有序集合） 元素不重复且带 score，按 score 自动排序 排行榜、延时队列、范围查询（ZRANGEBYSCORE）

三种特殊类型

类型 说明 典型用途
Bitmap（位图） 基于 String 的位操作 用户签到、活跃/在线统计、布隆过滤器基础
HyperLogLog 基数估算，固定占用 12KB，标准误差约 0.81% UV 独立访客统计（海量数据去重计数）
Geospatial（地理位置） 基于 Sorted Set，存储经纬度 附近的人、门店查找、距离计算（GEOSEARCH）

通用命令

KEYS

KEYS 命令用于查找所有符合给定模式 pattern 的 key

KEYS pattern

时间复杂度为 O(N)，且命令执行是单线程的，key 数量多时会阻塞其他请求，生产环境禁用，需要遍历 key 时改用 SCAN cursor [MATCH pattern] [COUNT count] 分批返回

pattern 描述
* 匹配多个字符
? 匹配一个字符

DEL

DEL 命令用于删除已存在的 key，不存在的 key 会被忽略，返回实际删除的数量

DEL key [key …]

EXISTS

EXISTS 命令用于检查给定 key 是否存在，返回 1 表示存在，0 表示不存在

EXISTS key [key …]

Redis 3.0.3 起支持一次传入多个 key，返回存在的个数

EXPIRE

EXPIRE 命令用于设置 key 的过期时间，单位以秒计，到期后该 key 会被自动删除

EXPIRE key seconds

返回 1 表示设置成功，返回 0 表示 key 不存在

等待 10 秒后再查询，key 已被删除：

相关命令：PEXPIRE（毫秒）、EXPIREAT / PEXPIREAT（指定时间戳）、PERSIST（移除过期时间，转为永久）

TTL

TTL 命令以秒为单位返回 key 的剩余过期时间

TTL key

返回值有三种：

返回值 含义
大于 0 剩余过期秒数
-1 key 存在，但没有设置过期时间（永久有效）
-2 key 不存在

不同数据类型的操作命令

String

字符串类型是 Redis 中最简单的存储类型

虽然表现形式都是字符串，但又可以分为：

  1. 普通字符串：Hello World
  2. 数值型字符串：10、3.14

不管哪种格式，底层都以字节数组形式存储。区别在于数值型字符串可以参与计算：整数可用 INCR / DECR 自增自减，浮点数只能用 INCRBYFLOAT 增加（没有对应的减命令，传负数即可）

对 3.14 执行 INCR 会报错 (error) ERR value is not an integer or out of range

Redis 的 Java 客户端

如果想通过 Java 操作 Redis，需要使用对应的 Redis 客户端

  1. Lettuce：基于 Netty，异步非阻塞，线程安全，是 Spring Boot 的默认客户端
  2. Jedis：同步阻塞，API 贴近 Redis 命令，轻量，但单个 Jedis 实例线程不安全
  3. Redisson：不只是客户端，还封装了分布式锁、分布式集合、延时队列等分布式对象

Jedis 连接池

原生的 Jedis 对象是一条连接，线程不安全，多线程下需要为每个线程分配一个实例；频繁创建和销毁连接开销较大，因此引入连接池

Spring Data Redis

Spring Data Redis 为 Redis 提供连接管理和 Repository 支持，屏蔽了不同客户端的差异，用统一的编程模型访问 Redis

Spring Data Redis 中提供了工具类 RedisTemplate，针对不同类型的数据提供了不同的操作对象。Spring Boot 默认使用 Lettuce 作为底层客户端

背景：验证码不能再存 Session 了之前生成验证码后是直接存进 Session 的（见《Spring Security Remember Me 与验证码》），服务端靠 JSESSIONID 把「这次生成的验证码」和「这个浏览器」对应起来。 现在 Session 已经禁用，服务端不记任何会话状态，于是验证码遇到一个最基础的问题： 服务端把验证码交给前端之后，下次请求带上来的验证码，怎么知道对应的是哪一次生成的结果？ Session 时代的答案是「同一个 JSESSIONID」，现在这个答案没了，那就自己造一个标识：生成验证码时顺便发一个 UUID， Redis 里存 captcha:{uuid} → 验证码，带 5 分钟 TTL uuid 返回给前端 登录时前端把它带回来，服务端拿 uuid 查出验证码，再和请求里的 captcha 参数比对 也就是说：用「Redis 的 key」替代「Session」，状态放到集中存储里，而不是绑在某次会话上。这和 JWT 的思路是一致的：Token 证明「身份是我签发的」，而 uuid 只负责「把我这次的验证码找...
